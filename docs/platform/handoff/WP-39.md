| 1 | Scope policy methods | `ScopePolicy` exposes `filterRecords`, `projectSnapshot`, `canReadObject`, `filterOrgSnapshot` | `SCOPE_POLICY` keeps the WP-08 interface (`readScope`, `filter`, `canReadObject`); the reader methods are on the exported class `ScopePolicyService` (the token's implementation), with `scopeContext` and `orgScopeContext` built once per request | `src/common/tokens.ts` belongs to WP-08; readers inject the exported class |
| 2 | Cross-organisation membership reads | F.6 needs to know whether a user has another active membership; F.10 allows platform scope only outside `authz` and `admin-users` | `MembershipDirectory` reads in a read-only transaction bound to no organisation and sets `app.user_id` (transaction-local) to each user in turn, so the C.4 policy's user clause shows exactly that user's membership rows; only a boolean leaves the service. ## Follow-ups

- WP-11 or orchestrator: `apps/server/test/int/identity/sessions.test.ts` line 388 expects `forbidden` for `GET /admin/audit-trail` by a Tenant Admin of an offboarding organisation. It held with the WP-08 deny-all evaluator; with WP-39's evaluator the Tenant Admin holds `audit_trail.metadata.read` and gets 200 (offboarding allows reads). The assertion should expect 200 (or use a member without an admin role). WP-39 cannot edit that file.
- WP-17: build `/ui/ms/{ms}` and `/ui/org` on the full data, then `ScopePolicyService.scopeContext` plus `projectSnapshot`, and `orgScopeContext` plus `filterOrgSnapshot` with `visibleCodesByMs` (owned codes and their up and down codes for own-scoped systems) and `exampleKeysByMs`. Refs of kinds `prep`, `cycle` and `drift` are kept for owner-scoped readers when their business id or ref code equals the first element of a kept tuple. `MS.mgr` must use active grants only: a pending grant may carry `is_primary`.
- WP-21 and WP-26: check `canReadObject` (or `canReadObjectIn` with the request's context) before `open`, `content` and `redirect`, and add the record behind a file with `addAuditorReadRefs`. WP-26 revocation: set `valid_until`, revoke the grant's sessions; the role resolver already ignores roles past `valid_until`.
- WP-25: after `PUT /me/org`, the persona switch and a change of the caller's own roles (own admin roles in `PATCH /admin/users/{id}`, revoking an own role), the session id and the CSRF token change; `PUT /me/org` and the persona switch return the new token in `Me`, the admin routes do not, so the client reads `GET /me` after them.
- WP-30: the guard's external auditor rule and `auditor.read` are covered here on probe routes; the generated RBAC suite can rely on `evaluateDetailed`.
- WP-11: `InvitationService.inviteUser` decides `is_default` with `hasMembership`, which inside a tenant transaction sees only the current organisation's rows, so an account invited by a second organisation can get a second default membership.
- WP-08 (or the orchestrator): `ScopePolicy` in `src/common/tokens.ts` could list the reader methods of deviation 1.

## Plan findings

- F.6 asks Tenant Admins' requests to know a user's memberships in other organisations, but F.10 and `eslint.config.mjs` allow platform scope only outside `admin-users` and `authz`. Deviation 2 stays within the RLS policy; a `SECURITY DEFINER` function `platform.other_active_membership(user, org) returns boolean` (C.4 owner) or adding `admin-users` to the allow-list would be simpler to review.
- D.3 lists 422 `LIC-USERS` for role grants, but a grant needs an active member, who is already counted; this build raises it on membership enabling and acceptance only.
- F.7 does not say whether a guest may call auth-only non-GET business routes (`POST /notifications/{id}/read`, `POST /tasks/{id}/complete`); this build refuses every non-GET business route for guests.
