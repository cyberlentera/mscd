# WP-02 handoff: developer infrastructure stack

## What was built

All files are under `deploy/compose/dev/`, the only path WP-02 owns.

| File | Content |
|---|---|

Run from a state with no `mscd-wp02` containers or volumes, on Docker 29.6.2 with Compose 5.3.1. `up -d --wait` takes about 35 seconds.

The block was also run verbatim under `bash -e` (exit 0), first on the original files, again after the first review fixes (fixed user ids, persistent NameID) and a third time after the second review fixes (README and handoff wording only), each time from a state with no `mscd-wp02` containers or volumes.

Checked beyond the acceptance commands:

- PostgreSQL: role attributes and settings match C.2 (`mscd_report` is `NOLOGIN`), schema `ext` owned by `mscd_migrator` with `pg_trgm` in it, `CREATE` on `public` denied to `mscd_app`, password sign-in of each login role through the published port, and a second run of the init script succeeds.
- S3 with SigV4: list buckets shows `mscd-vault`; put, get, list and delete work; a wrong secret and anonymous access get 403.
- OIDC: all five users sign in; ID tokens carry `email`, `email_verified: true` and `amr`; the authorisation code flow refuses a request without `code_challenge` and succeeds with S256; a wrong client secret gets 401.
- Fixed subjects: after a fresh `up -d --wait`, the ID token `sub` of the password grant is `00000000-0000-4000-8000-0000000000c1` for `rina`, `...c2` for `bagus`, `...c3` for `maya`, `...c4` for `hendra` and `...d1` for `sso.only`.
- `amr`: a password sign-in gives `["pwd"]`, in both the browser flow and the password grant. After the user enrols an OTP credential, it gives `["pwd", "otp"]`, also in both flows.
- SAML: an SP-initiated login with an unsigned HTTP-Redirect AuthnRequest from `mscd-dev-sp` returns an HTTP-POST response to the requested ACS URL with a signed response and a signed, unencrypted assertion. The response has a NameID of format `urn:oasis:names:tc:SAML:2.0:nameid-format:persistent` whose value is the user id (for example `00000000-0000-4000-8000-0000000000c1` for `rina`), the `email` attribute, audience `mscd-dev-sp` and the expected `InResponseTo`. The format stays persistent when the AuthnRequest asks for `emailAddress` or has no `NameIDPolicy`.
- Cookies: a request with host `localhost` or `127.0.0.1` gets `Secure; SameSite=None` sign-in cookies; a request with host `keycloak:58080` gets them without `Secure` and with `SameSite=Lax`.
- Mailpit accepts SMTP with and without a login; the API lists and deletes the messages.
- A `.env` in `deploy/compose/dev/` is read when Compose runs from the repository root.

`npm run check:text` does not exist yet (no root `package.json` while WP-01 runs). Every file of this WP is plain ASCII, so neither forbidden character occurs. `typecheck`, `lint` and `test` apply from WP-03 on; this WP has no Node code.

## Deviations and additions

| Item | Plan | Built | Reason |
|---|---|---|---|
| Published address | Ports only | Every port bound to `${MSCD_DEV_BIND_ADDRESS:-127.0.0.1}` | The passwords are public; the stack should not be reachable from the network by default. Set `0.0.0.0` to share it |
| Variable names | "`POSTGRES_PASSWORD` from `.env`", "ports from `.env`" | `.env` variables are prefixed `MSCD_DEV_` (`MSCD_DEV_POSTGRES_PASSWORD` feeds the container's `POSTGRES_PASSWORD`) | Shell variables win over `.env` in Compose; a developer's own `POSTGRES_PASSWORD` or port variables must not change this stack by accident |
| PostgreSQL health check | `pg_isready` | `pg_isready -h 127.0.0.1` (TCP) | The image runs the init scripts on a socket-only server; a socket check reports healthy before the roles exist |
| SeaweedFS health check | master `/cluster/status` | master `/cluster/status`, then S3 `/healthz`, then the `mscd-vault` folder in the filer | The master is up before the S3 gateway and the bucket; the acceptance check on port 58333 right after `--wait` needs both |
| Keycloak health check | as given | as given plus `Connection: close` | Without it a failing check waits for the keep-alive to end instead of failing fast |
| Valkey health check | `valkey-cli ping` | `valkey-cli ping \| grep -q PONG` | `LOADING` replies would otherwise count as healthy |
| `mscd_report` | `CREATE ROLE mscd_report NOLOGIN` (no password) | `NOLOGIN` with password `report-dev` preset; README shows `ALTER ROLE mscd_report LOGIN` | C.2 and D-31 create the role `NOLOGIN`; the dev stack mirrors production rights, and the preset password lets a developer enable the role for local reporting work with one statement. This line is the only content difference from the C.2 SQL |
| Keycloak storage | Not stated | No volume; the realm is imported whenever the container is created | Keeps `realm-mscd.json` the single source of truth. Admin console changes survive `restart` but not recreation (README) |
| `amr` claim | Not stated (brief asks for `email` and `email_verified`) | Client mapper `oidc-amr-mapper`, plus custom flows `mscd browser` and `mscd direct grant` whose password step carries reference `pwd` and OTP step `otp` | Keycloak sends an empty `amr` unless the steps carry references. With them, tests can exercise the `require_mfa_claim` and `accepted_amr` checks of F.5 with real values: `["pwd"]` for a password sign-in (not MFA proof, so the default `mfa_fallback = 'local_totp'` continues to the local TOTP step, as G.3 expects) and `["pwd", "otp"]` once the user has an OTP credential (MFA proof). Keycloak adds its built-in flows next to the custom ones on import (checked) |
| `sso.only` user id | Not stated | Fixed id `00000000-0000-4000-8000-0000000000d1`, outside the G.3 range | Deterministic subject for the `no_account` test |
| SAML persistent NameID value | Not stated | User attribute `saml.persistent.name.id.for.mscd-dev-sp` on each realm user, set to the user id | Keycloak otherwise generates a random `G-<uuid>` on the first SAML sign-in, so tests could not pre-register SAML subjects. The attribute is hidden in the admin console and admin API (unmanaged attribute under the Keycloak 26 user profile) but Keycloak uses it |
| `sso.only` email | "G.3 emails" (G.3 has no `sso.only`) | `sso.only@mscd.test` | Domain used by the other test-only accounts; no MSCD account has this email |
| Realm settings | Not stated | `sslRequired: none`, brute-force protection off, registration and password reset off | Plain HTTP from containers and tests; tests fail sign-ins on purpose |
| SAML client details | Signed assertions, NameID format persistent, `email` mapper | NameID format persistent and forced (`saml_force_name_id_format`), so the IdP sends it whatever the AuthnRequest asks for. Also signed responses, RSA-SHA256, AuthnRequest signature not required, forced POST binding, no encryption, no artifact binding | Matches F.9: no AuthnRequest signing, no encrypted assertions, HTTP-POST responses |
| Mailpit | Not stated | SMTP login of any user accepted, messages kept in volume `mailpit-data` (at most 5000) | The server may send with or without SMTP credentials |
| Valkey | Not stated | Append-only file on, RDB snapshots off | Queued BullMQ jobs survive a restart |

## Notes for later work packages

- WP-03 (owner of `db bootstrap` and `migrations/bootstrap/*.sql`): the dev database already holds the C.2 objects; `db bootstrap` against `postgres://postgres:postgres-dev@localhost:55432/mscd` must be a no-op apart from notices. If C.2 changes, update `postgres/init/00-roles.sql` in the same change (owner: whoever owns `deploy/compose/dev/**` then).
- WP-13 and WP-15: S3 endpoint `http://localhost:58333`, region `us-east-1`, path-style, bucket `mscd-vault`.
- WP-16 (`test/setup/keycloak.ts` imports this realm file):
  - Subjects (`sub`) are fixed: `rina` `00000000-0000-4000-8000-0000000000c1`, `bagus` `...c2`, `maya` `...c3`, `hendra` `...c4`, `sso.only` `...d1`.
  - On `localhost` and `127.0.0.1`, Keycloak 26 sets `Secure` and `SameSite=None` on its sign-in cookies even over HTTP. The test HTTP client must send them to `http://localhost` (`tough-cookie` 6 does this by default, `allowSecureOnLocal: true`). Without that, Keycloak answers "Cookie not found".
  - The issuer follows the request host. Use `localhost`, never `127.0.0.1`, for the issuer, the discovery URL and the browser.
  - `amr` is `["pwd"]` for a password sign-in, which is not MFA proof. With the default `mfa_fallback = 'local_totp'` the sign-in continues to the local TOTP step. The `amr` policy test must also set `mfa_fallback = 'reject'` on the provider to expect `mfa_required_by_policy`. For the positive case, give the user an OTP credential (for example through the `CONFIGURE_TOTP` required action), after which `amr` is `["pwd", "otp"]`.
  - The login form has id `kc-form-login` (fields `username`, `password`). Required actions arrive through a redirect to `/login-actions/required-action`.
- WP-19: NameID format is `urn:oasis:names:tc:SAML:2.0:nameid-format:persistent` (forced) and its value is the user id listed for WP-16, so SAML subjects can be pre-registered like the OIDC ones. IdP metadata at `http://localhost:58080/realms/mscd/protocol/saml/descriptor`, IdP entity id `http://localhost:58080/realms/mscd`, SP entity id `mscd-dev-sp`. For the unsigned-assertion test, set the client attribute `saml.assertion.signature` to `false` (and `saml.server.signature` to `false` if the test needs a fully unsigned response) through the admin API. The admin token comes from realm `master`, client `admin-cli`, user `admin`, password `admin-dev`.
- WP-22 and WP-24: Valkey `redis://localhost:56379`; Mailpit SMTP `localhost:51025`, API `http://localhost:58025/api/v1/messages`.
- WP-28 (demo overlay) can mount the same realm file with `KC_HTTP_PORT=18088` and `KC_HOSTNAME=http://keycloak:18088` as I.3 says. For a host other than `localhost` or `127.0.0.1` over plain HTTP, Keycloak sets its sign-in cookies without `Secure` and with `SameSite=Lax` (checked with host `keycloak:58080`), so the smoke browser with `--host-resolver-rules="MAP keycloak 127.0.0.1"` signs in over HTTP. The issuer is then `http://keycloak:18088/realms/mscd` for both the api and the browser.
