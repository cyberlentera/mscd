## Deviations and decisions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | `JOB_QUEUE` provider | Replace in `common.module.ts` or move to `JobsModule` | Replaced in `common.module.ts` (WP-08's file, as the WP-08 handoff and the orchestrator asked): the factory calls `createJobQueue` from `modules/jobs` | Many modules and tests load `TenancyModule` (and so `CommonModule`) without `JobsModule` |
| 2 | Test profile driver | `jobs.driver: pgboss` | In memory unless `MSCD_TEST_JOBS_DRIVER=profile`; then also no migrate step 3 and the worker refuses to start | J.8 runs jobs in process; existing suites rely on the in-memory queue; the API end-to-end stack (WP-27) sets the variable for separate api and worker processes |
| 3 | Singleton semantics on pg-boss | `singletonKey` | Queues use the `exclusive` policy (one created, retrying or active job per key); a send without a key gets a unique key | The E.1 contract; with pg-boss 12 a key alone does not deduplicate on standard queues, and policy queues treat a missing key as one shared key |
| 4 | Cron schedule keys | `tick:<utc hour>`, `ce:<utc hour>`, `av:<date>`, `pl:<utc date>` | Schedules carry the static key `cron:<name>`; the hour and date keys apply when the jobs are sent by hand | Cron templates cannot compute a key per firing; both drivers fire a schedule once per occurrence across workers |
| 5 | What is scheduled | Every E.2 job | Only jobs with a handler in the build (daily jobs and cron schedules) | Jobs without a handler would pile up; later WPs get scheduled by adding the handler |
| 6 | `notifications.dispatch` sweep | Every 5 minutes | Scheduled with envelope `orgId: null` once WP-24's handler exists | One cron for the installation; the handler must sweep every organisation for a null `orgId` |
| 7 | Anchor object key | `audit-anchors/<chain>/<date>.json` | `audit-anchors/<chain>/<date>-<seq>.json` | A second anchor on the same day (manual run, grown chain) would overwrite or hit object lock |
| 8 | Anchor frequency | An anchor per chain per run | None when the head is already anchored; none for a broken chain | Idempotency (J.8); an anchor of a rewritten head would vouch for it |
| 9 | Time windows with `demo.fixed_today` | `now()` | `windowNow`: the real time of day moved to the fixed date (`job-support.ts`) | The seeded `link_status_since` values sit days before the fixed date; with the real date every 72 hour window of the demo data had passed and eleven BCMS controls of ndt were downgraded |
| 10 | Downgrade scope | Entry in `implemented` without `keepsImplemented` | Only entries with at least one evidence record; BR-31 when any record is unverifiable, else BR-11; only when the system's edition activates that rule | No evidence is not expired evidence (TS 6.1 lowers entries whose evidence went out of date or became unverifiable) |
| 11 | BR-11 and BR-31 tasks | On downgrade | Opened for the records that caused a downgrade; closed by any recompute that sees the record valid (BR-31) or no longer expired or critical (BR-11) | E.3 "tasks close when the evidence is valid again" |
| 12 | BR-10 tasks | On expiry | Every expired document has one, also documents seeded as expired | One rule for every expired document; the demo parity shows they merge into existing chain items |
| 13 | Once-per-item notifications | `task_overdue` once per item; `evidence_aging` since the last sweep | Checked against stored notifications (`entity_ref.id`, and for ageing created on or after the production date) | Survives restarts and repeated runs without extra columns |
| 14 | Audit actions | Not named for job writes | Prep task creation `register.created`, due diligence expiry `register.updated`, task closing `task.completed`, all actor `system` | Closest F.11 actions |
| 15 | Rule task owner | Record owner | Null when the owner is no longer an active member (BR-45 Unassigned) | `assert_member` would reject the row and fail the whole job |
| 16 | Folder of tenant jobs | `modules/{jobs,freshness}` | `tasks.overdue` and `audit-prep.generate` live in `modules/jobs`, the freshness jobs in `modules/freshness` | Owned paths |
| 17 | Outbox retention | Rows older than 7 days | Relayed rows older than 7 days; rows never relayed stay for diagnosis | A row that cannot be relayed is a job that never ran |
| 18 | Export files | "marks expired" | Soft-deleted (`deleted_at`) | `export_file` has no status column; removing the vault object is WP-24's export cleanup |
| 19 | Cron retry limits | E.2 limit per job | Both drivers read the limit from `CRON_SCHEDULES` (`cronRetryLimit`): pg-boss `retryLimit`, BullMQ `attempts = limit + 1`; `audit.verify-chain` 2, `notifications.dispatch` 5, others 3 | The `JobQueue.schedule` signature (WP-08) stays unchanged |
| 20 | Outbox relay order | Oldest rows first | `ORDER BY attempts, id`: rows that keep failing sink behind new rows; each failure logs the attempt count | A full batch of rows that cannot be relayed (for example job names of a newer build after a rollback) no longer blocks newer jobs; no row is dropped |

## Plan findings

- E.3 and C.12 windows: WP-17's read model shows integrity codes only; if a read path ever evaluates `validForStatus`, it should use the same instant as the jobs (`windowNow`), or the demo data reads differently from what the jobs store.
- The `set_updated_at` trigger moves `updated_at` when a job stores derived columns (freshness and integrity of evidence and entries), so the weak ETags of those records change after a recompute that changed a value. A client holding the old ETag gets 412 on its next command for that record. The jobs write only changed values, which keeps this rare; a separate derived-state table would avoid it.
- E.2 lists keys such as `tick:<utc hour>` for cron jobs; cron templates cannot carry per-firing keys (deviation 4).
- `apps/server/test/fixtures/secrets/audit-anchor.key`, named by the demo and test profiles, still does not exist. The tests point `MSCD__AUDIT__ANCHOR_KEY_FILE` at `packages/pack-tools/dev-keys/anchor-signing.key` (key id `0abdc91769bacddd`, already in `dev-key-ids.json` and compiled into dev builds).
