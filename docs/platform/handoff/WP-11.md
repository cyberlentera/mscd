# WP-11 handoff: authentication, sessions and MFA

## What was built

| Area | Files | Content |
|---|---|---|
| Sessions | `apps/server/src/modules/identity/session.service.ts`, `platform-scope.ts`, `tokens.ts` | `SessionService`: sessions as `platform.session` rows behind a cookie of 32 random bytes (`__Host-mscd_session`, or `mscd_session` with `security.cookie_secure: false`; `HttpOnly`, `SameSite=Lax`, `Path=/`), only `sha256(value)` stored. `create`, `rotate` (new id, old row revoked as `rotated`, absolute expiry and persistence kept, a session already rotated or revoked cannot be rotated again), `touchProof`, `revoke`, `revokeUserSessions` (with an exception for the caller's session), `revokeOrganisationSessions` (current or authenticating organisation, optionally one user), `revokeGrantSessions`, `revokeProviderSessions`, `revokeUserSessions` also takes `states` to revoke only sessions in those states, `isOpen(trx, idHash)`, `setCookie` (persistent sessions get `Max-Age` up to their absolute expiry), `clearCookie`, `currentOf(request)`, `csrfTokenOf(request)`. The revocations switch the transaction-local platform scope on for their statement and back, so other modules call them inside their own `withTenant` transaction |
| Session resolution and CSRF | `session-resolver.ts`, `guest-otp.ts` | `SESSION_RESOLVER` (F.7): cookie, session (not revoked, idle and absolute expiry checked with `Clock.now()`; an expired row is revoked as `expired`), user (`active`, not deleted), then the organisation status rule: membership `active` and organisation `active`, or `offboarding` for `GET` and `exports.*` routes only, else 403 `organisation-inactive`. `last_seen_at` and `idle_expires_at` are written at most once per minute. `verifyRequest` (F.2): non-GET requests of a session must send `X-CSRF-Token` (SHA-256 compared in constant time with `csrf_token_hash`); public non-GET routes and `guest_otp` routes must come from the origin of `http.public_url` (`Origin`, else `Referer`); a request with neither header is refused when a page of another site could have sent it (a body with a CORS-safelisted content type, or a body without a content type: `crossSiteSendable`). `GuestOtpResolverRegistry` is the extension point for the guest one-time code caller (`auth: 'guest_otp'`) |
| Sign-in and passwords | `auth.service.ts`, `credentials.ts`, `local-login-policy.ts`, `password-hasher.ts`, `password-policy.ts`, `common-passwords.txt` | `POST /auth/login` with one generic 401 (`auth.invalid_credentials`) for unknown email, wrong password, disabled, invited or locked accounts (an unknown email spends one argon2 verification too); account lockout after 10 consecutive wrong passwords for 15 minutes; rehash of outdated hashes on sign-in; the local sign-in policy (`allowed`, `admins_only`, `disabled`): the session is pinned to the first allowing organisation (active organisations first, then the default membership, then the organisation order), a platform operator without memberships signs in without an organisation, otherwise 401 `auth.sso_required` with the providers of the user's organisations, only after a correct password. `POST /auth/logout`, `POST /auth/password/reset-request` (always 202; link `<public_url>/reset-password#token=...`, 30 minutes, single use; no email for unknown, inactive or SSO-only users; the email is sent in the background so the timing reveals nothing), `POST /auth/password/reset` (policy check, every session revoked), `POST /auth/password/change` (current password checked with the lockout, other sessions revoked). argon2id 19,456 KiB, 2 iterations, parallelism 1, 32 bytes. Policy: 12 to 256 characters, not the email or handle, not a common password (`isCommonPassword`): the list holds SecLists `10k-most-common.txt` (10,001 entries) and the 10,000 most common passwords of 12 or more characters from SecLists `xato-net-10-million-passwords-1000000.txt` (19,992 entries in all); besides exact matches it rejects a common word with digits or symbols around it (`password1234`, `2024summer!!`), also after undoing common character swaps (`p@ssw0rd2024`), a repeated common word or short unit (`passwordpassword`, `abcabcabcabc`), fewer than 4 distinct characters (`111111111111`) and runs of consecutive characters (`123456789012`). The list file starts with a header (lines starting with `#`, ended by the first empty line) holding the source, the SecLists commit and the SecLists MIT copyright and permission notice; `parseCommonPasswordList` skips it |
| MFA | `mfa.service.ts`, `totp.ts`, `recovery-codes.ts` | In-house RFC 4226 and RFC 6238 (SHA-1, 6 digits, 30 seconds, one step before and after; SHA-256, SHA-512 and 8 digits for the RFC vectors) and RFC 4648 base32. Secrets of 20 bytes sealed with `platform.key` (AAD `mfa:<userId>`); replay protection through `last_used_step` updated conditionally. Ten recovery codes `xxxx-xxxx-xx`, argon2id-hashed, single use, `auth.recovery_code_used` and a `security` email with the number left. Per-user second-factor lock: `mfa_failed_count` across sessions; the 10th consecutive failure answers 401 and locks for 15 minutes times 2 to the decayed level (at most 24 hours), the level decays by one per 24 hours since the last lock ended; while locked every attempt is 429 with `Retry-After` and the code is not checked; a success resets the count; every failure audits `auth.mfa_failed`, every lock `auth.mfa_locked` and emails the user. Per session: the route limit of 5 attempts per 5 minutes, and the 10th failure of one session revokes it (`mfa_failures`); the session's failures are counted in `platform.rate_limit_bucket` inside the verification transaction (`countSessionFailureIn(trx, ...)`), never through a second pool connection while the user's row lock is held. `POST /auth/mfa/verify`, `POST /auth/mfa/enrol/start` with the proof of `enrolmentProofNeeded`, decided under the user's row lock after checking the session is still open: none for the first factor of an `mfa_enrolment` session; from an active session the current code or the password unless the session proved one in the last 5 minutes; from an `mfa_enrolment` session of a user who has a confirmed factor (confirmed in another session meanwhile) only the current code, unless the session proved it in the last 5 minutes (a password is refused with `auth.proof_required`), `POST /auth/mfa/enrol/confirm` (the same rule checked again under the lock for a session that is not active; replaces an older factor and the recovery codes, ten new codes shown once, session rotated to `active`; on re-enrolment every other session is revoked as `mfa_reenrolled`, on a first enrolment the user's other sessions still in `mfa_enrolment` as `mfa_enrolled`, both with `auth.session_revoked`; `auth.mfa_enrolled` with `replaced`, `security` email). `resetFactor(trx, userId, ...)` for the F.6 MFA reset. `hasRecentProof` for identity linking |
| Invitations | `invitation.service.ts` | `inviteUser(trx, ...)`: a new account (`status invited`, no password, handle from the email) or an existing one, an `invited` membership with the admin roles, `LicenceGate.assertCanAddUser` in the same transaction, `user.created` and `user.invited`. A new account, or an existing one that was never activated (`status invited`), also gets an invitation (72 hours, single use, link `<public_url>/invite#token=...`); an active account gets only the `invited` membership (F.6: its owner accepts it after signing in), unless the caller passes `linkForActiveAccount` (the operator's `admin create-user` does). Templates: `password_reset`, `invitation`, `mfa_reset`, `guest_access_link`, `guest_code`, `mfa_enrolled`, `mfa_replaced`, `recovery_code_used`, `mfa_locked`, `password_changed`, `password_reset_done`, `identity_linked` |
| Other | `preferences.service.ts`, `sign-in-responder.ts`, `identity-infra.ts`, `auth.controller.ts`, `identity.module.ts`, `README.md` | `PUT /me/preferences` (merge; a null clears a stored key and writes nothing for a key never stored; every stored row, cleared ones included, counts towards 16 KiB) and `PreferencesService.get` for `Me.preferences`; `SignInResponder` builds the `LoginResponse` of a new session (cookie, next step, `Me` once active); `IdentityInfra` holds the services of other modules as optional dependencies; the module loads the password list at start and fails without it |

## Review fixes (round 2)

| Finding | Fix |
|---|---|
| Major: a session still in `mfa_enrolment` could replace a factor the user confirmed later in another session, without any proof, and so reach `active` with the password alone | Confirming the first factor revokes the user's other sessions still in `mfa_enrolment` (`mfa_enrolled`, audited). `enrol/start` decides the proof under the user's row lock with `enrolmentProofNeeded`: once the user has a confirmed factor, a session that has not passed the second factor must give the current code (or have proved it in the last 5 minutes); its password is not accepted, since the sign-in already proved it (deviation 17). `enrol/confirm` checks the same rule again under the lock, and `enrol/start` refuses a session revoked after the resolver read it. ## Deviations and additions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | CSRF token | 32 random bytes per session, hash stored | The token is HMAC-SHA256 of a fixed label keyed with the 32 random bytes of the session cookie; only its SHA-256 is stored and compared | `GET /me` (WP-39) must return `Me.csrfToken` after a page reload, and the server keeps only hashes; the derived value is as unpredictable as the cookie, which page scripts cannot read. `SessionService.csrfTokenOf(request)` returns it |
| 2 | Origin check | Public POST routes need a matching `Origin` (or `Referer`) | `Origin` decides when present (`null` never matches), else `Referer`. With neither header the request is refused (403 `csrf`) when a page of another site could have sent it: a body whose content type is CORS-safelisted (`text/plain`, `application/x-www-form-urlencoded`, `multipart/form-data`) or a body without a content type. A JSON body, or no body, is accepted | Older browsers, or a page with `Referrer-Policy: no-referrer`, can submit a form without either header, so those requests are refused. A JSON request needs a CORS preflight, which the api never answers, so only a program (command-line client, test runner) can send it without `Origin`; every real public POST route needs a JSON body. The product owner has not decided this yet (see Plan findings); if F.2 must refuse every request without either header, the last line of `verifyRequest` becomes an unconditional `throw` and the WP-08 unit test `test/unit/common/api-route.test.ts` ("mounts test-only routes", a body-less POST without `Origin`) must send the application's `Origin` |
| 3 | Organisation status rule | Business routes answer 403 `organisation-inactive` | Routes under `/api/v1/auth/` and the session routes `me.get`, `me.switch-org`, `me.membership.accept` and `me.preferences` are not business routes | A member of a suspended organisation can still log out, see who is signed in and switch to another organisation (D-26) |
| 4 | `PUT /me/preferences` | Store the preferences | Merge: given keys are upserted, `null` clears a stored key (the row keeps a null value, not returned by `PreferencesService.get`) and writes nothing for a key without a row; 413 when every stored row, cleared ones included, exceeds 16 KiB as one JSON object | `mscd_app` has no DELETE grant on `platform.user_preference` (C.4), so cleared rows stay and must count, or their number would have no bound. A DELETE grant (C.4 owner) would let a null remove the row |
| 5 | Per-session second-factor failures | Session revoked after 10 failures | Counted in `platform.rate_limit_bucket` (key `mfa-fail:<session hash>`, window the session's remaining lifetime) with the same upsert as the rate-limit store, run in the verification transaction | `platform.session` has no counter column; the count must not use a second pool connection while the transaction holds the user's row lock |
| 6 | Invitation for an account that has a password | `{token, password?}` | `password` is required and is the account's current password, checked with the lockout; it is never replaced and no session is revoked. `InvitationAcceptRequest.password` accepts 1 to 256 characters so a current password is not refused by the schema | An invitation link must not let anyone replace a password or skip the password proof |
| 7 | `admin create-user` | `--email --name --tenant-admin --org` | `--name` optional (default: the part before `@`), `--org` optional when exactly one organisation exists; an existing active account gets an invited membership and, unlike `POST /admin/users` (F.6), an invitation link too (`linkForActiveAccount`), accepted with its current password; an active member is refused | Matches the WP-03 skeleton; the operator can re-invite a person who left every organisation and so cannot sign in to accept a membership |

| 9 | Password failures outside sign-in | Not specified | A wrong current password (password change) or a wrong password given as re-enrolment proof counts towards the account lockout | One counter for every password guess |
| 10 | `auth.login` timing | Not specified | Written when the session becomes active (after the second factor or the first enrolment) with `secondFactor` (`totp`, `recovery_code`, `totp_enrolment`) | One entry per completed sign-in |
| 11 | Optional dependencies | Not specified | The identity services reach `TenantScope`, `TenantResolver`, `Clock`, `SecretBox`, `AUDIT_WRITER`, `LICENCE_GATE` and `ME_ASSEMBLER` through `IdentityInfra` as optional dependencies; without the database services the resolver authenticates nobody | The WP-08 request-pipeline unit tests load `IdentityModule` without a database (`test/unit/common/http-helpers.ts`) |

## Follow-ups

- WP-18: copy `apps/server/src/modules/identity/common-passwords.txt` whole into the server image next to `dist/modules/identity/` (or keep the source path); `IdentityModule` refuses to start without it. Its header is the SecLists MIT copyright and permission notice, which must ship with the list (do not strip comment lines); WP-33 may also list it in a third-party notices file of the release.
- WP-39: `GET /me` takes `csrfToken` from `SessionService.csrfTokenOf(request)` and `preferences` from `PreferencesService.get(userId)`; `PUT /me/org`, the persona switch and changes of the user's own roles rotate with `SessionService.rotate(trx, current.row, {organizationId, ...})` and `setCookie` (`currentOf(request)` gives the row); disabling a user calls `revokeUserSessions(trx, userId, 'user_disabled')`, removing or disabling a membership `revokeOrganisationSessions(trx, orgId, 'membership_removed', {userId})`; the MFA reset of F.6 calls `MfaService.resetFactor` after the Tenant Admin checks; `POST /admin/users` uses `InvitationService.inviteUser` without `linkForActiveAccount` and emails the link with the `invitation` template of `AccountMailer` only when `invitation` is not null (a new or never-activated account); for an existing active account `inviteUser` creates only the `invited` membership, which the user accepts through `POST /me/memberships/{org}/accept`, so the 202 answer stays the same and no link reaches another tenant's account; the D-26 check of `PUT /me/org` can use `localLoginAllowed` and `providerMethods` of `local-login-policy.ts`; `PATCH /admin/organization` must call `TenantResolver.invalidate`.
- WP-16 and WP-19: create SSO sessions with `SessionService.create(trx, {authMethod: 'oidc' or 'saml', identityProviderId, amr, authOrgId: <provider organisation>, organizationId, state})` where `state` is `mfa_pending` (`MfaService.hasConfirmedFactor`) or `mfa_enrolment` for the local TOTP fallback, then `setCookie`; the existing MFA routes finish the sign-in and audit `auth.login`. An `mfa_enrolment` SSO session follows the same enrolment rule as a local one: if the user has a confirmed factor by the time it enrols, it must give the current code. Identity linking uses `hasRecentProof(current.row, now)`; the `identity_linked` template exists; disabling a provider calls `revokeProviderSessions`. Invitation tokens are stored as `sha256(token)` (`tokens.ts`).

## Plan findings

- F.5 says nothing about a user with several sessions waiting for the first enrolment; this build revokes the others at the first confirmation and asks the current code (never the password) from a session that has not passed the second factor once a factor exists (deviation 17). The plan could state both rules in F.5.

- F.2 does not say what to do with a public POST that has neither `Origin` nor `Referer`. This build refuses the ones a page of another site can send and accepts JSON or body-less requests (deviation 2). This needs a product owner decision; if every such request must be refused, the change is one line in `session-resolver.ts` plus the WP-08 unit test named in deviation 2, and every non-browser client (WP-27, WP-31, smoke scripts) must send the application's `Origin`.
- F.4 asks for "the 10,000 most common passwords", which with a 12-character minimum rejects almost nothing; this build ships a longer list and normalised checks (deviation 16). F.6 does not say how a person with no active membership accepts an invited membership of an existing account (they cannot sign in); this build gives never-activated accounts a link (deviation 15) and the operator command a link for active accounts (deviation 7).
- D.3 `PUT /me/preferences` reads as a replacement, but C.4 grants no DELETE on `platform.user_preference`; this build merges (deviation 4).
- D.1 and F.7 do not define "business routes"; this build exempts the sign-in steps and the user's own session routes (deviation 3).
- F.3 asks for a per-session failure count that `platform.session` cannot hold; a column `mfa_failed_count` on `platform.session` would be simpler than the rate-limit bucket used here (deviation 5).
- `createPgPool` (`src/db/kysely.ts`, WP-08) sets no `connectionTimeoutMillis`, so any code that asks the pool for a second connection while its own transaction holds a row lock can stall the api when the pool is exhausted. This build no longer does so; a pool wait limit (for example 10 seconds) would turn a future mistake of this kind into errors instead of a hang (orchestrator or WP-08).
