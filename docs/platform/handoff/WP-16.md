# WP-16 handoff: OIDC sign-in and identity providers

## What was built

| Area | Files | Content |
|---|---|---|
| OIDC sign-in | `apps/server/src/modules/identity/oidc/oidc-sign-in.service.ts`, `oidc.controller.ts` | `GET /auth/oidc/{slug}/start`: 404 for an unknown, disabled or non-OIDC provider (or a kind the profile does not offer, or an archived organisation). An `?invitation=` token must name an unused, unrevoked, unexpired invitation of the provider's organisation, else the browser goes to `/login?error=invitation_invalid` and no transaction is written. Discovery, then an `auth_transaction` (`oidc_login`) with the SHA-256 of the state and of a browser binding value, the nonce, the PKCE verifier sealed with `platform.key` (`pkce:<transaction id>`), the relative `return_to` and the invitation id in `target_id`, 10 minutes. The binding value goes to cookie `mscd_auth_tx` (`HttpOnly`, `SameSite=Lax`, `Secure` with `security.cookie_secure`, `Path=/api/v1/auth/oidc/`, 10 minutes). Redirect to the authorisation URL (`response_type=code`, the provider's scopes, `state`, `nonce`, S256 challenge; `prompt=login` for links and invitations). `GET /auth/oidc/{slug}/callback`: `DELETE ... RETURNING` of the transaction by state hash (single use), binding cookie compared in constant time, expiry by the server clock, provider still usable, `openid-client` `authorizationCodeGrant` with expected state, nonce and verifier (issuer, audience, signature, expiry and the `iss` parameter are checked by the library), then the rules below. The binding cookie is always cleared. Every failure redirects to `/login?error=<code>` |
| Identity paths (F.8 step 4) | same | First match wins: (1) `user_identity (provider, subject)` exists: that user; with an invitation in the transaction it must be that user's invitation, which is then redeemed. (2) `oidc_link` transaction: the subject is linked to the transaction's user (`link_method = 'session'`, `linked_by` the user), `identity.linked`, `security` email `identity_linked`; a subject linked to another account is refused, one linked to the same user is kept. (3) Invitation: unused, unexpired, unrevoked, of the provider's organisation; a verified email of the token must equal the invitation email; link `invitation`, membership `active` after `LicenceGate.assertCanAddUser`, an `invited` account becomes `active`, invitation marked used, `identity.linked` and `membership.updated`. (4) JIT: the provider allows it, every `allowed_email_domains` entry is in `platform.verified_domain` for the provider's organisation, the token's verified email is under one of them, no non-guest account has that email; a new active account (handle from the email, display name from `name` or given and family name), an active membership without roles, link `jit`, after `LicenceGate.assertCanAddUser`; `user.created` and `identity.linked`. Otherwise `no_account`, also when an account with the same email exists (never linked by email) |
| MFA and session (F.5, D-26) | same, `oidc-rules.ts` | With `require_mfa_claim` the `amr` claim proves MFA when it contains `mfa` or at least two distinct values in `accepted_amr` (`['otp']` alone does not). Without a proof: `mfa_fallback = 'reject'` gives `mfa_required_by_policy`; `local_totp` continues to the local TOTP step. `require_mfa_claim = false` always continues to the local step. The account must be an active person with an active membership in the provider's organisation. The session (`auth_method = 'oidc'`, `identity_provider_id`, `amr`, `organization_id` and `auth_org_id` = the provider's organisation) is `active` with an MFA proof, else `mfa_pending` (confirmed factor) or `mfa_enrolment`; a session cookie presented with the callback is revoked (`signed_in_again`). Active: `auth.login` with method, provider id and slug, subject, `secondFactor: 'idp_mfa'` and `amr`, then a redirect to `return_to`. Pending: redirect to `/login/mfa#csrf=<token>` or `/login/enrol#csrf=<token>` (the web pages of WP-38 take the token from the fragment); the MFA routes of WP-11 finish the sign-in and audit `auth.login`. `user_identity.last_login_at` is stamped at every callback that gets this far |
| Failure codes | same | `expired`: unknown or replayed state, expired transaction, missing or wrong binding cookie, provider slug of another transaction, a link callback without the signed-in transaction user. `idp_error`: an `error` answer of the provider, a failed code exchange or ID token, a provider disabled meanwhile, Entra `tid` mismatch or missing claims, a subject linked to another account (link), unexpected errors. `no_account`, `invitation_invalid`, `mfa_required_by_policy` as above. Refusals of a known transaction audit `auth.login_failed` in `platform.audit_log` with the provider's organisation (`entity_type` `identity_provider`, `after_data` `{method, flow, error, reason}`); unknown states are only logged |
| Identity linking | `oidc-sign-in.service.ts`, `identity-link.registry.ts` | `POST /me/identities/{slug}/link`: the provider must be enabled and belong to an organisation where the session user (a person) is an active member, else 404; the session must have verified the password or a TOTP code in the last 5 minutes (`hasRecentProof` of WP-11), else 401 `auth.proof_required`. The starter of the provider's kind (`IdentityLinkRegistry`, OIDC registered here) writes an `oidc_link` transaction with the user, sets `mscd_auth_tx` and returns `{redirectUrl}`; 503 when discovery fails. The callback requires the same signed-in user in the same browser (session cookie and binding cookie) and redirects to `/` |
| Discovery | `discovery.ts` | `OidcDiscovery`: `openid-client` 6.8.8 `discovery` with `ClientSecretPost` (or `None` without a secret), 10 seconds per request, cached one hour per provider and per settings (issuer, client, sealed secret, `updated_at`, so an edited provider is discovered again at once on every replica); `identity.oidc.allow_insecure_http` adds `allowInsecureRequests`, otherwise an `http:` issuer fails with `insecure_issuer` before any request. Failure reasons safe to show: `insecure_issuer`, `invalid_issuer`, `unreachable`, `timeout`, `invalid_metadata`, `issuer_mismatch`, `http_error`. `invalidate(providerId)` and `clear()` (test reset) |
| Login page providers | `auth-providers.service.ts` | `GET /auth/providers`: enabled providers of kinds in `identity.providers`, of organisations that are not archived or deleted, ordered by organisation position and label. `tenancy.mode = multi`: one organisation chosen by `?org=` or by the domain of `?email=` in `platform.verified_domain` (a domain verified for several organisations names none); without one the list is empty. `single`: every provider, or those of the organisation the query names. `local` is true when the profile offers local sign-in and the chosen organisation does not have `local_login = 'disabled'` |
| Provider administration | `apps/server/src/modules/admin-idp/` | `GET`, `POST /admin/identity-providers`, `PATCH /admin/identity-providers/{id}`, `POST /admin/identity-providers/{id}/test` (`idp.manage`), every query in the session organisation's tenant transaction (forced RLS of `platform.identity_provider`) and filtered by its id; another organisation's provider is 404. Create: kind offered by the profile (422 `idp.kind_disabled`), settings checked as a whole (400: `openid` in the scopes, Entra needs a tenant id, `require_mfa_claim = false` only with `local_totp`, JIT needs domains and is not offered for SAML, SAML certificates must parse as X.509 and are stored as PEM), OIDC discovery before saving (422 `idp.discovery_failed` with the reason in both languages), JIT domains verified for the organisation (422 `idp.jit_domain_unverified`, `affected` lists the missing ones), client secret sealed with `platform.key` (AAD `idp:<providerId>`, the id is chosen before sealing), a slug in use anywhere is 409 `idp.slug_taken` (the slug index is installation-wide), `idp.created` audited without secrets. Update: changed fields only, the result checked as a whole, discovery again when issuer, client id or secret change, the row re-read under lock (409 `idp.changed` when it changed between the checks and the write), a new secret re-sealed, disabling revokes the provider's sessions (`revokeProviderSessions`, `idp_disabled`), `idp.updated` with before and after (no secrets; `clientSecretReplaced`, `sessionsRevoked`), discovery cache entry dropped. Test: fresh OIDC discovery with `{ok, issuer, endpoints}` (authorization, token, userinfo, jwks, endSession) or `{ok: false, message}`; for SAML the single sign-on and SP metadata URLs and the validity of the certificates |
| Module wiring | `identity/oidc/oidc.module.ts`, `admin-idp/admin-idp.module.ts` | `OidcModule` (controller, `OidcDiscovery`, `IdentityLinkRegistry`, sign-in and provider list services; exports discovery and the registry) is imported by `AdminIdpModule`, which `feature-modules.ts` already loads. ## Deviations and additions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | Rate limit of the start route | F.3 lists none | 30 starts per 15 minutes per address (the `POST /auth/login` limit), 429 listed in the contract | Every anonymous start writes a transaction row until the cleanup job removes it; the limit bounds what one client can make the server store |
| 2 | `prompt=login` | Not specified | Sent for link transactions and for starts with an invitation | A link or an invitation binds an identity to an account for good; an earlier provider session in the browser (someone else's, on a shared computer) must not be linked silently |
| 3 | Error codes | F.8 step 6 lists the codes | Transaction problems (unknown, replayed or forged state, expiry, binding cookie, provider of another transaction, link callback without the transaction's signed-in user) are `expired`; provider and token problems are `idp_error`; a full licence during JIT is `no_account`, during invitation redemption `idp_error` | The login page has only these codes (WP-38); `expired` tells the user to start again |
| 4 | Link errors | `/login?error=<code>` | The same redirect, also for a user who stays signed in (the web then opens the application and the message is not shown) | F.8 step 6; a page for linking results is web work outside this package |
| 5 | Pre-registered subject with an invitation | Step 4 "first match wins" | An existing link wins, and the invitation in the transaction is still redeemed when it belongs to the same user (membership active, invitation used); an invitation of another user is `invitation_invalid` | Otherwise a Tenant Admin's pre-registration would stop the invitee from ever activating the membership through the provider |
| 6 | `IdentityProviderTestResult` | `{ok, issuer, endpoints}` | Adds optional `message` with the failure reason | The Tenant Admin needs to know why the test failed; no response body is shown |
| 7 | Contract of `me.identity.link` and `admin.idp.update` | 401, 404; 404, 422 | Link adds 503 (discovery failed); update adds 409 (`idp.changed`) | Both answers exist |
| 8 | Linkable providers | Not specified | Providers of any organisation where the user is an active member, not only the session's current one | A member of an SSO-only organisation who signs in locally elsewhere can prepare the link before switching |
| 9 | Session of an IdP MFA proof | Not specified | `mfa_at` stays null | The IdP's MFA is not a local password or TOTP proof, so it does not replace the F.5 proof of re-enrolment or linking |
| 10 | Users with `mfa_required = false` | F.5: every user needs a second factor | Without an IdP proof and with `local_totp`, the session is active at once when neither `app_user.mfa_required` nor `identity.local.mfa_required` asks for a factor, exactly as local sign-in (`AuthService.secondFactorRequired`) | One rule for both sign-in methods; `mfa_required` is true for every account this build creates |
| 11 | Membership of a linked account | Not specified | A linked account must be an active person with an active membership in the provider's organisation, else `no_account` | The session is pinned to that organisation (D-26); without the membership every business route would answer 403 |
| 12 | `GET /auth/providers` in single-tenant mode | D.2 states the multi-tenant rule | `?org=` or a verified `?email=` domain narrows the list when given, otherwise every provider | The web passes `?org=` of the address in every mode |
| 13 | SAML provider administration | D.3 admin routes take `IdentityProviderRequest` with `saml` | Supported in full here: certificates checked and stored as PEM, a SAML test reports endpoints and certificate validity; sign-in stays with WP-19 | The admin routes belong to this package |

## Follow-ups

- WP-19 (SAML): `SamlModule` (`identity/saml/`) is not loaded by anything yet. The simplest mount is one line in `apps/server/src/modules/admin-idp/admin-idp.module.ts` (`imports: [OidcModule, SamlModule]`), a file of this package: the orchestrator must allow WP-19 that change (or make it). Register the SAML link starter with `IdentityLinkRegistry.register('saml', starter)` in `onModuleInit` (inject the registry exported by `OidcModule`; import `OidcModule` in `SamlModule`); `POST /me/identities/{slug}/link` then works for SAML providers. SAML provider rows come from the admin routes with `saml_idp_certs` as PEM text. `GET /auth/providers` already lists SAML providers. Reuse in tests: `KeycloakAdmin.updateClient('mscd-dev-sp', {attributes: {'saml.assertion.signature': 'false'}})` (returns the previous settings), and `keycloakSignIn(new KeycloakBrowser(), <HTTP-Redirect URL>, user)`, which returns `{kind: 'post', action, fields}` with `SAMLResponse` and `RelayState` for the ACS. The identity paths of `oidc-sign-in.service.ts` (link, invitation, JIT refusal) are private to it; a SAML implementation follows the same rules (F.9).
- WP-11 (identity module, finished): F.8 step 5 asks `auth.login` to carry the provider and the subject. For sessions that end at the local TOTP step, `MfaService.activate` writes `identityProviderId` but not the subject (the session row has no subject column). A lookup of `user_identity` by provider and user in `activate`, or a `subject` column on `platform.session`, would close it; the callback already records the subject in `identity.linked` and `auth.login_failed`, and in `auth.login` when the IdP proved MFA.
- WP-22: `cleanup.expired` should delete `platform.auth_transaction` rows past `expires_at` (unfinished sign-ins and links leave them; a callback deletes its own).
- WP-27: `POST /test/reset` should call `OidcDiscovery.clear()` (exported by `OidcModule`) with the other in-memory caches.
- WP-14: the seeded `keycloak` provider must seal its client secret with `SecretBox.seal(secret, {purpose: 'idp', providerId})` using the row's id, store the issuer exactly as Keycloak reports it (`http://keycloak:18088/realms/mscd`, no trailing slash) and keep `oidc_scopes` with `openid`. Keycloak's redirect URI is `<http.public_url>/api/v1/auth/oidc/keycloak/callback` (the realm allows `*`).
- WP-30 or a product owner decision: the discovery test lets a Tenant Admin make the api request `<issuer>/.well-known/openid-configuration` on any host it can reach. Results show only the reason category, never a response body, but in multi-tenant SaaS an egress rule (refusing private and loopback addresses unless the host is in `network.egress_allowlist`, checked when connecting) would remove the probe.

## Plan findings

- F.3 has no limit for the OIDC start route although each call writes a row (deviation 1).
- F.8 does not say how a pre-registered subject redeems an invitation (deviation 5) or whether linking and invitation flows should force a fresh provider sign-in (deviation 2).
- The modules of the identity subfolders (`oidc/`, `saml/`, `guest/`) have no place in `feature-modules.ts` or `identity.module.ts`; this package mounts `oidc/` through `admin-idp`, and WP-19 needs the same (follow-up above).
