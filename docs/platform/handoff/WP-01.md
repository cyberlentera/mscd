## Deviations and additions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | `apk upgrade` in the runtime stage | Not in the plan (the on-premise work added it after the plan was written) | `APK_UPGRADE` takes `true`, `auto` or `false`, default `auto`. The step runs `apk update` first: when it succeeds, `apk upgrade` must succeed in both `true` and `auto`; when it fails (a mirror that cannot be reached or is blocked by a proxy, or a TLS certificate that is not trusted because the `build_ca` secret is missing or wrong; `apk` prints the cause just above), `true` stops the build with a message naming the `build_ca` secret, `APK_UPGRADE=false` and `--no-os-updates`, and `auto` prints two `WARNING` lines that point to those `apk` messages and keeps the base image packages. Both messages name the two causes neutrally, because `apk update` exits with the same status for both (exit 2 for "TLS: server certificate not trusted" in the base image without the CA). `false` skips the step; any other value stops the build. The apk index cache is removed in the same layer | The sandbox egress policy denies `dl-cdn.alpinelinux.org`, so with the former default `true` the verbatim acceptance build could not pass here, nor could the web builds of WP-18 and WP-28. Release bundles do not depend on the default: `build-bundle.sh` passes `APK_UPGRADE=true`, or `false` with `--no-os-updates`, and the Trivy gate runs either way. The header example of `web.Dockerfile` for a release build by hand passes `APK_UPGRADE=true` |
| 2 | Runtime stage | Unchanged | One line added after `nginx -t -q`: `rm -rf /tmp/nginx.pid /tmp/*_temp` | The configuration test runs as root and left a root-owned `/tmp/nginx.pid`. With a plain `docker run` (no tmpfs on `/tmp`) NGINX as user 101 then stopped at start-up with "open() /tmp/nginx.pid failed (13: Permission denied)", so the acceptance health check failed. Compose and Helm mount a tmpfs or emptyDir on `/tmp`, which hid the defect |
| 3 | Lockfile | `npm install` at the root, then compare | The root lockfile was seeded from the former `app/package-lock.json` before `npm install` | A fresh resolution could move ranges such as `^5.3.0` to newer releases; seeding keeps every resolved version, which B.2 step 4 requires |
| 4 | `.dockerignore` | `node_modules`, `dist`, test output, `deploy/dist`, `project/uploads`, `chats` | Also `.git`, `.github`, `*.tsbuildinfo`, logs, `.env` files (not `.env.example`), `apps/server/src/generated`, the Helm schema cache, `project/screenshots` (15 MB), `apps/web/e2e` and `apps/web/playwright.config.js` | Smaller context (2.7 MB) and no secrets in it; test files were already excluded by the old `app/.dockerignore`, and leaving them out keeps the web build cache valid when only tests change |
| 5 | Web sources in the image | `npm run build -w @mscd/web` | The build stage copies `apps/web/` only | Nothing else is imported today. When the web imports another workspace (the `@mscd/shared` alias of WP-38), that workspace must be copied in `web.Dockerfile` too (WP-18 owns `deploy/docker/**` from wave 7) |
| 6 | `check:text` | `node tools/scripts/check-text.mjs docs` | Runs that command when the file exists, otherwise prints "not available" | Brief allows it; `tools/scripts/**` belongs to WP-03 |
| 7 | Converter | `--out` | Also `fileURLToPath` instead of `URL.pathname` (paths with spaces or non-ASCII characters), `--help`, strict option parsing | Robustness; generated output is unchanged |

`npm ci` reports two audit findings, both in the pinned dev tooling: esbuild 0.21 (moderate, development server only) through Vite 5.4.21 (high). The fix is Vite 6 or later, which A.1 defers ("framework upgrades are a later step"). Neither package is in the image; the image holds only the built static files.
