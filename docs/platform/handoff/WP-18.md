## Fix round 1

Review findings fixed:

- Major, API name resolved only at start: `40-mscd-runtime.sh` now writes a resolving upstream (deviation 11). Checked by hand on a separate network: a stub api with alias `api` answered through the web container, was removed and replaced by one at another address, and the web container reached the new one within 3 s (the old address answers 503 until the 10 s resolver validity or the failed connection triggers a new lookup). Also checked: an IP address or `[IPv6]:port` upstream gets no `resolve` and no resolver; `MSCD_API_RESOLVER='1.1.1.1, fd00::53'` is written as `resolver 1.1.1.1 [fd00::53]`; a non-address `MSCD_API_RESOLVER` stops the start; with `--dns-search corp.test` and an api reachable only as `svc.corp.test`, `MSCD_API_UPSTREAM=svc:3000` is written as `svc.corp.test:3000`; an unresolvable name starts NGINX and answers the 503 problem. `smoke.sh` now recreates the api at a new address as its last check.
- Minor, error log on static paths: `error_log /dev/stderr crit` moved from the `/api/` location to the `http` block, so it covers every request. The request of the finding (`GET /reset?token=...` with `Content-Length: 20000`) now leaves only the redacted access log line; `smoke.sh` checks it.

## Fix round 2

- Minor, `MSCD_API_RESOLVER` with a port: every entry (and every `nameserver` line of `/etc/resolv.conf`) must now parse as a plain IPv4 address (four numbers from 0 to 255) or a plain IPv6 address (hex groups, at most one `::`, an optional trailing IPv4 part such as `::ffff:192.0.2.1`). `1.1.1.1:53`, `[fd00::53]`, `256.1.1.1` and `fd00:::1` stop the start with the script's own error; ports are not accepted and port 53 is used. The header of the script and `deploy/docker/README.md` say which forms are accepted.
