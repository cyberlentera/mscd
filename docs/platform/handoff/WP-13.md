# WP-13 handoff: storage gateway and Managed Vault

## What was built

| Area | Files | Content |
|---|---|---|
| Run mode | `apps/server/src/cli/storage-gateway.ts`, `src/gateway/gateway-app.ts` | `mscd-server storage-gateway`: `GatewayModule` on its own Fastify application on `gateway.port`. `tls.mode: mtls` serves HTTPS with `requestCert` and `rejectUnauthorized` (installation CA of `gateway.tls.ca_file`, TLS 1.2 or later); `off` is plain HTTP and refused at start unless `demo.enabled`. Request headers up to 96 KiB (`X-MSCD-Put`). Health and readiness also on the metrics port |
| Gateway runtime | `src/gateway/gateway-server.module.ts` | `GatewayRuntime` loads `storage.key` (`gateway.kms.file`, previous keys for rotation), checks the token files, builds the adapters, registers the `/v1` routes, the readiness checks `storage-key` and `vault-bucket` (when the Managed Vault is enabled) and the metrics `mscd_gateway_calls_total` and `mscd_gateway_call_duration_seconds`. `checkGatewayProfile` refuses TLS off without demo mode and non-default provider base URLs whose host is not in `network.egress_allowlist` (outside demo mode). A missing key or token stops the start with a configuration error. `GATEWAY_ADAPTER_FACTORIES` lets tests add adapters |
| Authentication | `src/gateway/auth.ts` | Bearer token compared in constant time with `gateway.token_files[0]` and `[1]`, read on every call so a rotation needs no restart; with mtls the verified client certificate must be `CN=mscd-api` or `CN=mscd-worker` (403 `caller` otherwise) |
| Routes | `src/gateway/routes.ts` | Every D.5 endpoint, validated with the shared `gateway` schemas. Order of a call: token and certificate, body, tenant data key, credential opened with the binding check (D-08), adapter, `validateConfig`, scope root inside the configured roots (`outside-root`), adapter operation. Problems are `application/problem+json` with the D.5 slugs, `reason` and `retryAfter` (`Retry-After` header). One log line per call `{event: 'gateway.call', orgId, repositoryId, adapter, operation, callerCn, outcome, latencyMs, requestId}`. A refused upload closes the connection. `/v1/anchors` only for `CN=mscd-worker` |
| Crypto | `src/gateway/crypto/data-keys.ts`, `credentials.ts`, `chunked.ts` | `DataKeyService`: tenant data keys wrapped with `storage.key` (AAD `dek:<orgId>`, the `TestDataKeyIssuer` format), unwrapped keys cached five minutes, `rewrap`. Credentials sealed with the tenant data key, AAD `cred:<orgId>:<repositoryId>:<configSha256>`, recomputed on every call. Vault chunk encryption of F.11: per-object content key sealed with `obj:<orgId>:<objectId>`, 64 KiB AES-256-GCM chunks, nonce = 4-byte prefix plus 8-byte counter, AAD = content id, chunk index and final flag |
| File type, streams | `src/gateway/file-type.ts`, `src/gateway/streams.ts` | Type from the first 4 KiB: PDF, PNG, JPEG, GIF, WebP, DOCX, XLSX, PPTX, ZIP, plain UTF-8 text; HTML, SVG, XML and everything else `application/octet-stream`. `ContentMeter` computes SHA-256, counts bytes against `maxBytes` and keeps the first 4 KiB while the upload passes (no temporary file) |
| Adapters | `src/gateway/adapters/types.ts`, `index.ts`, `managed-vault/vault-adapter.ts`, `managed-vault/vault-store.ts` | `StorageAdapter` with one method per D.5 operation (optional ones answer `unsupported`, `pin-version` answers `{result: 'unsupported'}`), `AdapterRegistry` and `ADAPTER_FACTORIES`. Managed Vault on S3 (path-style, configurable endpoint): keys `<config.prefix><uuid>` inside `tenants/<orgId>/`; put streams through meter and encryptor into a multipart upload, then a server-side self-copy stores `mscd-sha256`, `mscd-size` and `mscd-type`; stat, stream (first chunk decrypted before the answer starts), copy-within (server-side copy, content key re-sealed for the new object id), rehash, list by folder label, ensure-folder (labels only), anchors with `If-None-Match: *` |
| Gateway client (api, worker) | `src/modules/storage/gateway-client.ts` | `HttpGatewayClient` (`GATEWAY_CLIENT`): undici, token read on every call, mTLS agent from `storage.gateway.tls`, https required with mtls and http only with off; `X-Request-Id` passed on; problems become `GatewayProblemError` (keeps `gatewaySlug`, `reason`, `retryAfter`; api slug per a fixed mapping), transport failures `GatewayUnavailableError` (503) |
| Descriptors, data keys | `src/modules/storage/gateway-context.ts`, `http-data-key-issuer.ts` | `StorageGatewayContext`: `tenant(trx, orgId)` from `platform.tenant_key`, `repository(trx, row)` with the active sealed credential, row lookups by id and slug; `repositoryConfigSha256`. `HttpDataKeyIssuer` (and `httpDataKeyIssuer(config)` for commands) implements `DataKeyIssuer` for `TenantProvisioner` |
| Repository administration | `src/modules/storage/repositories.service.ts`, `storage.controller.ts`, `repo-oauth.ts`, `storage-policy.ts` | The 14 routes of the `storage` area: list (`RepositoryView`), create (adapter enabled and licensed, id patterns, roots naming existing systems, vault prefix inside the organisation, duplicate slug 409), patch (a change of the binding config revokes the credential), credentials (kind per adapter, OAuth client id equal to `config.oauthClientId`, sealed by the gateway, certificate expiry, previous credential revoked), test (gateway `test-connection`, connection status and messages stored, references, next check 02:30 local), reauthorize and the OAuth callback (`repo_oauth` transaction, binding cookie `mscd_repo_tx`, PKCE verifier sealed with `platform.key`), move requests (personal repositories, `move_request` to every Tenant Admin), object metadata list |
| Routing | `src/modules/storage/routing.service.ts` | `RoutingService.resolve(trx, {msId, classification, objectKind})` (A-37, default repository, then the organisation vault); list, create, patch, approve, reject with BR-38 confirmation, four-eyes and the single-admin rule (A-50) |
| Read model helpers | `src/modules/storage/repository-view.ts`, `index.ts` | `repositoryActions`, `repositoryStatus`, `repositoryModesText`, `routingModeLabel`, `repositorySummary`, `repositoryUsage`, `toRepositoryView`, `listRepositoryViews`, `REPOSITORY_TYPE`, `MODE_LABELS` (G.5 `REPOS`, `ROUTING`) |
| Keys commands | `src/cli/keys.ts` | `keys generate --out <dir> [--force]` (platform.key, storage.key, gateway.token, audit-anchor.key, audit-anchor.pub; secrets mode 0400; prints key ids), `keys rewrap [--storage] [--platform]` (tenant data keys under the current storage.key; TOTP secrets, IdP client secrets and open PKCE verifiers under the current platform.key; as the migrator with platform scope), `keys rotate-gateway-token [--current] [--previous]` (default `gateway.token_files`) |

## Deviations and additions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | Vault encryption header | `{"v":1,"alg":"A256GCM-CHUNK64K","ck":"<sealed>","np":"<prefix>"}` | Adds `"cid"`: the id in the chunk additional data, the object id where the content was first encrypted | `copy-within` is a server-side copy: the ciphertext keeps its chunk binding and only `ck` is re-sealed for the new object id ("re-encryption header copy") |
| 2 | Vault metadata | Not stated | `mscd-enc`, `mscd-folder`, `mscd-created` and, unless metadata minimisation, `mscd-name` at upload; `mscd-sha256`, `mscd-size`, `mscd-type` by a server-side copy of the object onto itself after the upload | Hash, size and type are known only after the last byte; S3 metadata cannot change otherwise |
| 3 | Vault version label | Not stated | `PutResult.versionLabel` is `v1` (every vault object is immutable) | The gateway does not know `evidence.file_sequence`; WP-21 writes `v<file_sequence>` |
| 4 | `RehashResult` | `{hashValue, matches}` | Adds `detail: 'decryption_failed'`; `hashValue` is then the SHA-256 of the stored ciphertext and `matches` is false | A changed or truncated object cannot be hashed as plaintext; WP-23 records `hash_mismatch` either way |
| 5 | Gateway problems | Slugs only | Extension `reason`: `credential-binding`, `credential-kind`, `credential-missing`, `tenant-prefix`, `caller`, `token` (shared `GATEWAY_PROBLEM_REASONS`) | The api and tests need to tell refusals apart |
| 6 | Token failures | Not stated | 403 `forbidden` with `reason: 'token'` | D.5 has no 401 slug |
| 7 | Binding config | "config without display fields" | Top-level `display`, `displayName`, `label` and the `path` label of each per-system root are left out; site, drive, root folder, OAuth client and every root folder id bind. A repository PATCH revokes the credential only when this hash changes | A renamed folder label is not a different location |
| 8 | OAuth exchange | The gateway exchanges the code and checks drive and root | The gateway core opens the client credential with the binding check and calls the adapter's `exchangeOAuthCode`, then seals `{clientId, clientSecret, refreshToken}` | The Google calls belong to the Google Drive adapter (WP-15); until it lands the endpoint answers 422 for `google_drive` |
| 9 | Consent URL | Not stated | `https://accounts.google.com/o/oauth2/v2/auth` for Google's token URL, otherwise the origin of `gateway.providers.google.token_url` plus `/o/oauth2/v2/auth` (the mock providers); scope `drive.file`, offline access, forced consent, PKCE S256. The client id comes from `config.oauthClientId`, which the OAuth client credential must equal | No profile key names the authorisation endpoint and the api cannot open sealed credentials |
| 10 | OAuth callback | Delete by state hash, then require user, cookie and expiry | One `DELETE ... RETURNING` whose `WHERE` holds the state hash, kind, user, organisation, binding cookie hash and expiry. A mismatch leaves the transaction in place. Redirect `/storage` on success, `/storage?oauth=failed` or `?oauth=denied` otherwise. Cookie `mscd_repo_tx`, `HttpOnly`, `SameSite=Lax`, path of the callback, 10 minutes | Someone else's callback must not burn the admin's consent; "changes nothing" holds literally |
| 11 | Routing approvals | BR-38 and four-eyes need a second Tenant Admin | At most one active rule per scope (system, classification, object kind); activation supersedes the others. A change to an active rule that needs approval is a new pending row; such a change may not alter classification or object kind (409). The approver must hold `tenant_admin`; the same person gets 422 (`rule: BR-38` on BR-38 rows, `messageKey: storage.routing.same_person`). A pending row is changed only by its requester, with the approval check run for that person, so it stays pending unless the edited change needs no approval at all; a PATCH of a pending row by anyone else is 409 `conflict` with `messageKey: storage.routing.pending` (decide it with approve or reject). The requester's edit does not change the pending row in place: the row becomes `superseded` and the edited change is a new row (pending, or active when it needs no approval), whose `storage.routing.requested` entry carries `replaces: <old id>`; approve or reject of a superseded id is 409 `conflict` with `messageKey: storage.routing.superseded`, so an approval always applies to the version the approver loaded. PATCH, approve and reject lock the row (`FOR UPDATE`), so an edit never overwrites an approval committed meanwhile. Four-eyes applies to a Tenant Admin who is MS Manager of an affected system (an organisation-wide rule affects every system) when the organisation has two or more Tenant Admins; with one, the change applies and `storage.routing.approved` records `{approval: 'single_tenant_admin'}`. BR-38 applies to a rule into a `managed_vault` repository for classification `restricted` or any, when the vault is the provider's cloud (SaaS; in demo mode the organisation's `demo_deploy_label`) | `storage_routing_rule` has no column that points from a pending row to the rule it replaces |
| 12 | Repository status at creation | Not stated | Provider repositories start `failed` with "No credential set"; the vault starts `ok`. `RepositoryView.credentialSet` is true only when the active credential is bound to the current config | A repository without a working credential is not usable |
| 13 | Move requests | BR-30 notification | Only for `personal` repositories; otherwise 422 `business-rule` with `messageKey: storage.move_not_personal` and no `rule` (BR-30 is a warn-and-allow rule in D.1, so its id is not used for this refusal); a `move_request` notification to every active Tenant Admin; `count` is the number notified | BR-30 concerns personal storage |
| 14 | Connection test | `CommandResult` from `RepositoryTestResult` | Gateway problems (`unsupported`, `forbidden`, `unreachable`, `rate-limited`) become a `failed` result stored on the repository with a bilingual message; an unreachable gateway is 503. `nextCheckAt` is the next 02:30 in the organisation's time zone (E.2 `link-health.repository`) | The administrator sees why the test failed |
| 15 | Unlicensed or disabled adapter | 422 | Not enabled: 422 `business-rule` with `messageKey: storage.adapter_not_enabled`; not licensed: 422 `LIC-FEATURE` | One problem per cause |
| 16 | Anchors | Object lock when supported | Written with `If-None-Match: *`; an identical body again returns the same location, a different body goes to `<name>-2.json` and so on; with object lock and no default retention rule the object gets governance retention of 3650 days. With TLS off (demo) any authenticated caller may write anchors | An anchor is never overwritten; demo has no certificate names |
| 17 | `keys rewrap` | Re-wraps tenant data keys and re-seals secrets | Options `--storage` and `--platform` (default both); as the migrator with platform scope; secrets re-sealed: `mfa_factor`, `identity_provider.oidc_client_secret_sealed`, unexpired `auth_transaction.code_verifier_sealed`. ## Plan findings

- C.6 `storage_routing_rule` cannot link a pending change to the rule it replaces (deviation 11). A nullable `replaces_rule_id` would allow a pending change of classification or object kind.
- I.1 has no profile key for Google's authorisation endpoint (deviation 9); `gateway.providers.google.auth_url` would remove the derivation.
- D.5 has no slug for a missing or wrong token (deviation 6).
- With `tls.mode: mtls` the service port 8443 needs a client certificate, so probes and Compose health checks must use `/readyz` on the metrics port 9464 (served by every run mode). I.3 says "healthchecks with `wget ... http://127.0.0.1:<port>/readyz`"; for the gateway the port is 9464.
