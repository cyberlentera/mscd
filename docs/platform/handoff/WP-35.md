## Deviations and decisions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | BR-17 on assignment | Warning | Built from the BR-17 catalogue text when the rule is active (`RuleEngine.isActive`), without a `@BusinessRule` provider | WP-36 registers BR-17 as an error for register edits; one rule has one provider |
| 2 | BR-22 | Registered by WP-35 and listed by WP-36 | Registered here; `SharedChangeGuard` is the one entry point and answers 409 `confirmation-required` (D.1), never 422 | Two providers for one rule are a start-up error of the engine |
| 3 | Due date of preparation tasks and cycle items | `AssignmentRequest.dueAt` nullable | 400 when null for `prep` and `cycle` | `due_at` is NOT NULL on both tables |
| 4 | Unassigned document review | Holder `none` | `pending_holder_user_id` null, so the chain item falls back to the owner | A null pending holder means "no review assignment"; asserted as a known parity difference |
| 5 | Complete-action | Clears the pending action | `pending_action` null, `action_completed_at` and `action_completed_by` set, `action_due_at` kept; drift rows get `resolved_at` | Keeps the history; the chain item disappears as in the sample |
| 6 | Open dependants | "for example a risk with open treatments" | Risk: treatments not closed; metric: quality objectives; prioritized activity: BIAs; BC plan: exercises not performed; finding: corrective actions not closed or cancelled; document: BC plans and activities in `complete` that name it as output | The relations of C.6 where a dependant still needs the record |
| 7 | BR-16 author | "approved by its own author" | Submitter of the version in review, else of the version in force, else the creator of the register entry | Seeded versions have no submitter; a newly registered document without a version is authored by its creator |
| 8 | Next review date on approval | Not stated | Moved to today plus 365 days when empty or not in the future | Otherwise an approved document past its date is expired again at once (BR-10) |
| 9 | Document links | `linkedMs` | The path system must be listed (422 `documents.path_system_not_linked`) and holds the primary link; other systems need `document.manage` there (403) and the `integrated_mode` licence feature | F.7 and D-15 |
| 10 | BR-42 recipients | "affected holders" | Holders whose chain items changed from not after to after the audit, plus owners of preparation tasks newly flagged `violates_br43`; `n` per holder is that number; notifications are not digest | Only holders whose situation changed are notified |
| 11 | Reminder rows | E.5 | The notification is created first and the `reminder` row references it | `reminder` is insert-only for `mscd_app` (C.4 revokes UPDATE) |
| 12 | Bulk reminders | One reminder per holder | One `reminder` row per item and holder (BR-50 is per record key), one notification per holder listing up to ten items; `count` counts holders with at least one item sent | Matches the sample count and the throttle per record |
| 13 | Preparation task creation audit | Not stated | Action `prep_task.updated` with `after.created: true` | `AUDIT_ACTIONS` has no creation action for preparation tasks |
| 14 | Another user's task | "the task's owner" | 404 | Tasks are listed for their owner only (D-29) |
| 15 | Summary BR-46 member | WP-20 follow-up | Optional member, only for full-scope readers | Owner-scoped readers see their own records only |

## Follow-ups

- WP-36 and WP-37: do not register BR-22 (the engine refuses two providers of one rule). `SharedChangeGuard.assertConfirmed` (export of `src/modules/registers`) is the shared check; WP-36's own check in `risk-registers/rules.ts` uses `RuleEngine.isActive` and the same 409 shape without a provider, which is compatible. The generic delete route of this package already handles every register kind (`POST /ms/{ms}/records/{entityType}/{id}/delete`).
- WP-36: the assignment warning for BR-17 reads `ruleMessages('BR-17')`; if WP-36 changes the BR-17 text, both stay in step.
- WP-25: commands return `ref.etag`; send it as `If-Match` on the next command. Reminders return `changed: []`, `count` and a message pair; bulk reminders return `data.skipped`. A 409 `confirmation-required` carries `affected` slugs; repeat with `confirm: true`. Document approval is `POST /ms/{ms}/documents/{id}/transitions {to: 'approved'}`.
- WP-24: reminder and `audit_date_changed` notifications are not digest and queue `notifications.dispatch`; `prep_task_assigned` is digest.
- WP-30: `POST /reminders` with a record of another system is 404 (tested here); the RBAC matrix rows for `record.complete_action`, `prep_task.update` and `cycle_item.update` own grants are enforced in the services.
- WP-37: audit events created here get an `entity_ms_link` primary row; prep task generation (`audit-prep.generate`) should send `prep_task_assigned` the same way.
