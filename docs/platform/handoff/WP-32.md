# WP-32 handoff: per-screen read endpoints

## What was built

| Area | Files | Content |
|---|---|---|
| Service | `apps/server/src/modules/read-model-api/screen-read.service.ts` | `ScreenReadService`: one tenant transaction per request runs `ScopePolicyService.scopeContext` (404 unknown system, 403 no role), loads the system with the WP-17 loader (`loadOrgData` with the bundle), derives the full snapshot with `buildSystemSnapshot` (D-04), projects it with `ScopePolicyService.projectSnapshot`, and reads the few stored fields the snapshot does not carry: evidence targets, activity clause and expected outcome, event type and outcome, preparation tasks with the BR-43 flag, findings with their event and owner, drift severity and message, repository names, holders' roles. `audit.pending.all` and `audit.pending.aggregate` are checked through `PERMISSION_EVALUATOR` |
| Projections | `screens.ts` | One function per endpoint over `ScreenData` (`full` and the caller's `view` snapshot): `implementationSummary`, `applicabilityPage`, `documentsPage`, `gateItems`, `phaseActivities`, `nextAuditEvent` and `heroNumbers`, `stageReadiness`, `stageRecordsPage` (open items, then ready records), `pendingOf`, `pendingPerPerson`, `pendingAggregate`, `chainFrom`, `surveillanceEvent`, `cycleItems`, `driftPatterns`, `evidencePage` |
| Helpers | `query.ts`, `texts.ts` | Server search `q` (every word in code, title, owner name, note; the web's `match` rule) and paging; the response language from `Accept-Language` (`id` or `en`, by quality) and the bilingual labels |
| Routes | `read-model-api.controller.ts`, `read-model-api.module.ts`, `README.md` | The 14 routes of D.3 "Read model per screen" through `@ApiRoute` with the route definitions of `packages/shared/src/api/readmodel.ts`; `GET /audit/event/next` answers 204 without a body when no event is planned |
| Contract | `packages/shared/src/api/readmodel.ts` | Two changes, see deviations 1 and 2 |

Endpoint rules:

| Endpoint | Rule |
|---|---|
| `/implementation/summary` | Cards: implemented of all requirements (label by unit), partial plus complete, gate items (label with the pack's gate name), approved of all documents, expired documents; `criticalEvidence` and `unverifiableEvidence` as two counts (A.4 5.13); phases with counts and a derived text; current phase (UI 2.6); maturity per clause 4 to 10 from the stored readiness and the open items per clause (A.4 5.14) |
| `/applicability` | Requirement fields of UI 1.5 plus `ref` and, from E.3 `entryEvidenceState` over the entry's `evidence_target` rows, `lastEvidence`, `freshness`, `integrity`. `group` is the theme code (`A.8`) or the clause number (`8`) |
| `/documents` | Document fields plus `ref` and the requirements (visible to the caller) implementing the document; `type` is the `doc_type` code; `due_within` keeps documents whose review date is at most that many days ahead (overdue ones included, the web's `docs30`) |
| `/gates` | Gate items with `ref` and `affected`: the activities blocked by the item, then the activities of the next gate phase that are not verified (BR-12) |
| `/phases/{n}/activities` | Activities with derived status (D-13), `ref`, stored clause and expected outcome, output document (when visible); 404 for an unknown phase |
| `/audit/event/next` | TS 9.4 next event; numbers are the chain hero (open, overdue or missing, after audit, ready = records minus open items) |
| `/audit/stages` | Per stage: `rec`, open, pending, overdue (not pending), after, `ready = max(0, rec - open)`, `pct`, earliest due date not in the past, the auditor question |
| `/audit/stages/{key}/records` | TS 9.3 records: the stage's open items (status of D-12), then its ready records (implemented or not applicable requirements, approved documents, evidence that is neither unverifiable nor expired or critical, entity records without a pending action); `file` with repository name and link status for documents and evidence |
| `/audit/chain` | A stored chain by id, else a stored chain containing the code, else a chain built from a requirement, evidence, document or chain record (UI 2.10); node status from the full derivation, `clauseAtRisk` for overdue and missing nodes; nodes outside the caller's scope as `{stage, hidden: true}`; 404 when nothing is found or no node is visible |
| `/audit/pending` | `owner` given: that person's open items (anyone for themselves, others need `audit.pending.all`); no owner: everyone per holder (`audit.pending.all`), sorted by overdue, then open; `aggregate=unit`: counts per stage and business role (`audit.pending.aggregate`) |
| `/surveillance/events/{id}` | The event, its preparation tasks (BR-43 flag) and its findings: those raised at the event and, for the next event, the open certification audit findings to close |
| `/surveillance/cycle` | Items of the given cycle (404 when the system has none with that id), default the latest |
| `/surveillance/drift` | Patterns with rows (stored `drift_result` rows, or the live lists of A.4 5.15); without `rule` only active patterns, with `rule` that pattern (404 for an unknown code) |
| `/evidence` | UI 1.7 fields plus `ref` and the A-05 integrity status |

## Deviations and decisions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | `readmodel.audit.next-event` response | `NextAuditEvent`, errors `[204, 404]` | `NextAuditEvent.optional()` | The development-build response check of the `@ApiRoute` interceptor validates the handler's return value against `response`; the 204 answer has no body |
| 2 | `PendingAggregate.role` | `BusinessRole` | `BusinessRole` or null | Unassigned items and holders without a role in the system have no role; dropping them would make the counts disagree with the chain |
| 3 | Numbers for own-scoped readers | Not stated | Every list and number comes from the caller's projected snapshot (`projectSnapshot`), so it equals what that caller's `GET /ui/ms/{ms}` shows (TS 9.6 per reader): cards count the owner's records, stage `open` counts the owner's items while `rec` and phase counts stay those of the full data (D-04, as WP-17 keeps them) | One derivation per number; the web computes its screens from the same projected snapshot |
| 4 | External auditors | D-34 projection | Same rule: requirements, documents and pack evidence without owner fields; no gates, phases, cycle, drift, stage records or preparation tasks; stage readiness shows the projection's numbers (no open items); chain nodes of their projection without holder and due date, every other node hidden | `projectSnapshot` removes pending data; the endpoints never add it back |
| 5 | Chains for own-scoped readers | "nodes outside the user's scope are hidden" | Only records the reader owns or holds are visible; records they reference are hidden too (`GET /ui/org` `CHAINS` keeps referenced codes, without holder or status) | Node holders and statuses are record data |
| 6 | Pending without `owner` | Everyone's list needs `audit.pending.all` | 403 for readers without it (also Top Management, who uses `aggregate=unit`); `owner` equal to the caller is open to every reader | D.3 permissions |
| 7 | Stage records | TS 9.3 records with `status` filter | Without a filter, open items and ready records (the page total equals the stage's `rec` for entity, requirement, document and evidence stages); the justification stage has no ready rows (UI 2.5) | TS 6.9 `ready` is a status of the same list |
| 8 | Drift patterns | "Active drift patterns" | Without `rule` only patterns with at least one row; with `rule` that pattern even when it has none | The client can show an empty rule it asked for |
| 9 | Applicability `freshness`, `integrity`, `lastEvidence` | Read from stored columns (TS 9.5) | Derived per request with E.3 `entryEvidenceState`, like every other value of the read model | Stored columns are written by `freshness.recompute` (WP-22); the derivation gives the same values without depending on the job having run |
| 10 | TS 9.5 per-system summary tables | Stored aggregates | Not built; every request derives from the loaded rows (50 to 300 ms per request on the demo data) | WP-17 performance target holds; caching stays a later step |
| 11 | `PendingRecord.state` | TS 9.3 free text | Requirement or document status label, freshness and integrity labels for evidence, "Action open" or "No open action" for entity records | The stored records have no state text of their own |
| 12 | Top Management | "Pending data as aggregates only" (F.7, Q-8) | Holder names and due dates are kept only on records Top Management holds; every other holder comes as null (stage records, chain nodes) or `none` (gates, drift rows, cycle items, preparation tasks), with no due date where the field allows null; `owner` naming someone else on stage records finds nothing; the per-person list stays 403 and `aggregate=unit` gives counts | Otherwise a Top Management reader could rebuild the per-person pending list from `GET /audit/stages/{key}/records?owner=` |

## Follow-ups

- WP-25: the per-screen endpoints are optional for the controller (it renders from `/ui/*`); they serve clients that need server paging and search. `Accept-Language` decides the language of every text.
- WP-30: the RBAC suite can add `audit.pending.all` and `audit.pending.aggregate` cases on `GET /ms/{ms}/audit/pending` (403 without them, the `owner` equal to the caller allowed) and the external auditor rules of deviation 4.
- WP-22: once `freshness.recompute` runs in tests, a check that the stored `applicability_entry` columns equal the derived `lastEvidence`, `freshness` and `integrity` of `/applicability` would close deviation 9.
