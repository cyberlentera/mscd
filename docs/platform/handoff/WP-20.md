# WP-20 handoff: implementation commands and rule engine

## What was built

| Area | Files | Content |
|---|---|---|
| Rule decorator | `apps/server/src/modules/rules/business-rule.ts` | `@BusinessRule(id, {severity})` on a provider class whose `check({trx, msId, params, input})` returns a violation (`vars`, `localized`, `messages`, `ref`, `affected`, `data`) or null. Severity `error` (422 `business-rule`), `warning` (D.1 `warnings`) or `flag` (reported only, BR-46) |
| Rule activation | `rules/rule-activation.ts` | `RuleActivationService`: a pack rule (BR-01 to BR-50) is active for a system when `ref.rule_activation` of the system's `framework_version_id` has it `active`; its `params` come along. Platform rules (`LIC-*`, `VERIFY-SELF`, `NOT-A-MEMBER`, `SOD-SELF-GRANT`) are always active with `{}`. Read once per transaction |
| Rule engine | `rules/rule-engine.ts`, `rules/rules.module.ts`, `rules/index.ts` | `RuleEngine` (global module) finds every `@BusinessRule` provider through `DiscoveryService` (two providers for one rule are an error). `evaluate(trx, rule, input, {msIds, ref})` runs the rule for each system given where it is active (all linked systems of a shared entity, TS 3.5) and returns findings; `enforce` throws `BusinessRuleError` (with `messageKey` `rule.<id>`) on the first error finding and returns one warning per distinct message; `mergeWarnings`, `warningsOf`. Calling a rule without an implementation is a programming error |
| Messages | `rules/messages.ts` | `RULE_MESSAGES`: English and Indonesian text of BR-01 to BR-50 (digest 6.2 to 6.4, the digest's user messages where it gives one) and of `LIC-USERS`, `LIC-MS`, `LIC-FEATURE`, `LIC-BINDING`, `VERIFY-SELF`, `NOT-A-MEMBER`, `SOD-SELF-GRANT`; variables in braces with per-language defaults (`ruleMessages(rule, vars, localized)`), so every message reads well without context; `ruleMessageKey(rule)` |
| Applicability commands | `apps/server/src/modules/implementation/applicability.service.ts` | `POST /ms/{ms}/applicability/{id}/transitions`: record through `RecordResolver` (`forUpdate`), `If-Match`, the C.13 row the caller performs (`pickTransition`: full grant, or own grant on an own record, else 403; no row 409, or 422 with a machine rejection), required members (400), VERIFY-SELF (actor differs from `coalesce(completed_by, owner)`), BR-02 before `implemented`, BR-01 through `entryEvidenceState` (E.3), BR-03 warning on `not_applicable`; sets `completed_by`/`completed_at`, `verified_by`/`verified_at`, clears completion on the rejection `complete` to `partially_implemented` (the reason becomes the status note), `is_applicable` and the exclusion justification for `not_applicable`; one `applicability.transition` entry with from and to (A.4 5.1); `freshness.recompute` queued in the transaction. `PATCH /ms/{ms}/applicability/{id}`: owner (`MembershipService.resolveHandle`, `none` unassigns), justifications, gate flag and reason, note, frequency (`operating_criteria`, checked against the edition's `evidence_frequency_rule`), risks (linked to the system) and documents (linked or organisation-wide) replaced in request order with soft deletes, applicability with its status (`not_applicable` needs a justification; applicable again is `not_started`), BR-02 when applicability or risks change, BR-03 warning; one `applicability.updated` entry with the changed values; `freshness.recompute` when status or frequency changed. `POST /ms/{ms}/applicability`: a catalogue item or requirement of the active edition (422 otherwise), 409 for a live entry of the same target, owner and frequency checked, `operating_criteria` row, `applicability.created`, idempotent through the route's `Idempotency-Key` |
| Activity and phase commands | `implementation/activity.service.ts` | `POST /ms/{ms}/activities/{id}/transitions`: as above with BR-12 (an earlier critical gate phase with an activity that is not verified, D-13), BR-40 (output document from the request code, the stored link, or the document the template code names in the system's register; an unknown requested code is BR-40 too), VERIFY-SELF (actor differs from the completer and the owner, A-48), BR-39 (the blocker names a current gate item of the read model's `bundle.gates`, A-27), BR-47 warning (approved output on a blocked activity, or a verified activity whose output is not approved); rejection needs `rejectReason` (400) and clears completion; every move into `in_progress` clears the completion (also one carried through `blocked`); unblocking clears the blocker and, for an activity that was never started (no completion and no audit history in `in_progress` or later), runs BR-12 too, so `not_started` to `blocked` to `in_progress` cannot open a locked phase; from `not_started` to `complete` writes two `activity.transition` entries (A.4 5.12). `POST /ms/{ms}/phases/{n}/verify`: a transaction advisory lock per (system, phase) so concurrent confirmations write one entry; 404 for a phase without activities, 422 BR-12 with the sample's text when not every activity is verified, else one `phase.verified` entry per change of the phase ("Phase n verified"), and "Phase n is already verified" when the last confirmation is newer than every activity change; `changed` is empty (the phase state is derived). `gateConsistencyIn(trx, org, ms)` gives the BR-46 flag (blocked activities of the gate phase against open gate items) |
| Rule implementations | `implementation/rules/applicability.rules.ts`, `rules/activity.rules.ts`, `rules/index.ts` | BR-01, BR-02, BR-03 (phrases of `params.phrases` in every language, a justification made only of listed phrases, or shorter than `params.minLength`, default 10 characters), BR-12, BR-39, BR-40, BR-46 (flag), BR-47 (warning), VERIFY-SELF, registered as providers of `ImplementationModule` |
| Shared steps | `implementation/command-support.ts`, `implementation/evidence-state.ts` | `pickTransition`, `assertRequires`, `refOf` (RecordRef with the new weak ETag), `commandResult`, `enqueueFreshness` (singleton `fr:<org>:<ms>`, 5 second delay, sent with the transaction), `windowNowOf` (validity windows on `demo.fixed_today`, as the freshness jobs measure them); the E.3 inputs of one entry (`loadEntryEvidence`, `evidenceStateOfEntry`) |
| Routes and module | `implementation/implementation.controller.ts`, `implementation.module.ts`, `index.ts`, `README.md` | The five WP-20 routes of `packages/shared/src/api/implementation.ts` (unchanged) through `@ApiRoute`; `ImplementationModule` imports `ReadModelModule` and exports `ApplicabilityService` and `ActivityService` |

Updated rows write a new `updated_at` (`greatest(clock_timestamp(), updated_at + 1 ms)`), so every successful command changes the ETag, and the `ref` of the result carries it.

## Deviations and decisions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | BR-02 effect | Digest: save blocked until a risk is linked; A.4 5.2: the engine sets `holds_gate`; D.3: 422 BR-02 on transitions and PATCH | A new applicable entry (the create request has no risks) holds the gate with `gate_reason` "No risk-based justification", lifted when a PATCH links a risk; a PATCH that sets `isApplicable` or `riskCodes` and leaves an applicable entry without a risk is 422; a transition to `implemented` of an applicable entry without a risk is 422. Completion is not blocked | The sample's ABMS requirements carry no risks; blocking completion would break `markComplete` there, while verification is where the risk-based justification matters. The BR-02 message says so: the entry cannot be verified and holds the gate until it is linked to a risk |
| 2 | BR-03 | Phrase dictionary per language (A-07) | Exact phrase of any language after normalisation, a justification made only of listed phrases, or shorter than `params.minLength` (default 10 characters) | Two-letter answers such as "no" are not in the pack lists |
| 3 | BR-39 | Blocked without a reference or reason is rejected | A missing reference or reason is already 400 by the shared schema; the 422 BR-39 path is a reference that names no current gate item of the system (A-27, the read model's `bundle.gates`) | Gives the rule a server-side check |
| 4 | BR-40 | Reject without `output_document_id` | The command links the document the template's output code names when the system's register holds it; an unknown requested code is BR-40 | Seeded activities whose output document exists complete without a code, as in the sample |
| 5 | Phase verification | "message when nothing to do" | Phase state stays derived (D-13); a successful verification writes `phase.verified` and returns `changed: []`; a repeat with no activity change since returns "Phase n is already verified" | Nothing in the bundle changes; the audit entry records who confirmed the phase |
| 6 | `changed` | Systems whose bundles reload | The system of the path (entries and activities belong to one system) | Applicability entries and activities are not shareable |
| 7 | PATCH applicability and status | Not stated | `isApplicable: false` moves the entry to `not_applicable` (needs a justification, 400 otherwise); `isApplicable: true` on a `not_applicable` entry moves it to `not_started`, through the `applicability.manage` rows of C.13 | Keeps `is_applicable` and the status consistent |
| 8 | Rejection note | Reason recorded | The reason of `complete` to `partially_implemented` becomes the status note (shown as `note`) and is in the audit entry; `rejectReason` of an activity is in the audit entry | The UI shows the note on the requirement |
| 9 | BR-46 | Flag in the summary | `ActivityService.gateConsistencyIn` and the `BR-46` flag rule; `ImplementationSummary` has no member for it yet | WP-32 owns the summary schema and endpoint |

## Follow-ups

- WP-32: add the BR-46 flag to `ImplementationSummary` (for example `gateConsistency: {blocked, openGateItems, flagged, messages}` for MS Managers) from `ActivityService.gateConsistencyIn(trx, org, ms)` (export of `src/modules/implementation`).
- WP-35, WP-36, WP-37: register rules with `@BusinessRule('BR-xx', {severity})` in your own module and call `RuleEngine.enforce(trx, rule, input, {msIds, ref})` with every linked system of shared entities; build messages with `ruleMessages` (BR-22 `systems`, BR-41 `date`, BR-42 `n`, BR-50 `last`, `next`). `pickTransition` and `assertRequires` in `implementation/command-support.ts` follow the WP-05 lookup rule and can be copied; they are not exported from the module index.
- WP-22: `freshness.recompute` receives `{msId, entryIds}` from every applicability command; the job may also call `RuleEngine.isActive` instead of its own activation query.
- WP-25: commands return `ref.etag` of the new version; send it as `If-Match` on the next command of the same record. Phase verification returns `changed: []` and a `message`.
- WP-27 and WP-30: `markComplete` on an ISMS activity behind the unpassed gate phase 4 (for example 9.7) is 422 BR-12 in API mode; the sample allows it.
- Existing problem messages of other modules (`NotAMemberError`, licence errors) keep their own texts; they can switch to `ruleMessages` when their owners next change them.
