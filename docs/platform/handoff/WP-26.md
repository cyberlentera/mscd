## Deviations and decisions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | Access link token | 32-byte token, SHA-256 stored | `<organisation id, 22 characters base64url><32 random bytes base64url>` (65 characters, inside the contract's `LinkToken` pattern); the SHA-256 of the whole token is stored | Grants live in tenant schemas; the public start route reads the one schema the prefix names instead of searching every tenant. The prefix is not secret and the 32 random bytes keep their strength |
| 2 | Returning guest with several active grants | "a new code when an active grant exists" | The newest active grant of the address (across organisations) gets the code | One code transaction and one binding cookie per browser; the other grants stay usable through their own sessions or a later request |
| 3 | Per-grant limit | 5 an hour per grant | One bucket (`auth.guest.code`) for start and login together, counted before the grant's state is checked, so failed link uses on a known grant count too; an exceeded login sends nothing and answers as usual, an exceeded start answers 429 | The login answer must not reveal anything (F.14 step 4) |
| 4 | Manifest repository | The system's default repository | The default repository when it can store files (`stored` or `pass_through` modes), else the organisation's Managed Vault | `PUT /v1/objects` needs a storing mode; the demo BCMS library (`gd`) is zero-transit and link only |
| 5 | Archive | ".tar.gz for the Managed Vault" | Built when the manifests are in the Managed Vault; holds the vault copies and both manifests (copies in provider repositories stay in their pack folders) | The api streams only vault and pass-through content; provider copies are already in the provider's pack folder |
| 6 | Copies | `copy-within` per repository | One `copy-within` call per file | A failure (for example a pinned version that changed meanwhile, which the m365 adapter refuses) becomes that file's exception instead of failing the whole repository |
| 7 | Copy objects | A `storage_object` per copy | `external_item_id` = the new item, `external_version_id` null, hash and type of the source (same bytes), folder from the copy location, link status `intact` | `copy-within` returns only the new id and location; the link health job (WP-23) refreshes provider facts |
| 8 | Grant expiry | Expiry ends sessions and role | The role ends by `valid_until` at once (the role resolver ignores it); every guest session expires no later than its grant (absolute expiry capped at sign-in, rotations keep it), so the session resolver refuses it at the grant's end and `cleanup.expired` revokes it within the hour; the membership and open codes are ended when grants are listed or created, and code requests and code checks refuse expired grants | No E.2 job owns a grant sweep; the remaining lazy part (membership status, the grant's `expired` audit row) grants nothing; see follow-ups |
| 9 | System links and undated evidence | Not stated | Evidence recorded as a system link (no storage object) is an exception ("Recorded as a system link; there is no file to copy"); evidence never produced (`produced_at` null) is not in a pack | A-10 lists everything that is not copied; E.7 takes evidence produced within the cycle |
| 10 | Scope filter | `scope.clauses` or `scope.codes` | `codes` match requirement or catalogue codes exactly; `clauses` match a requirement's clause group, a catalogue theme code, or a code equal to the clause or starting with `<clause>.` or `A.<clause>.`; both lists are combined with OR | D.2 gives the fields without their matching rule |
| 11 | Downloads by role | `ms.read`, same scope | External auditors download manifests and archives of ready packs; Top Management (no file access, TS 7.3) and owner-scoped readers (manifests list every record) get 403 | D-34, F.6 |
| 12 | Folder name clash | Not stated | A second pack of a system with the same label gets ` (2)`, ` (3)`, ... | Two packs on one day would otherwise share a folder |
| 13 | Guest code failures | 5 attempts | Each wrong code writes `auth.login_failed` (`method: 'guest'`, `reason: 'wrong_code'`); the guest routes answer 401 without a `messageKey` (the web page maps the status) | `AUTH_MESSAGE_KEYS` belongs to the WP-11 part of `auth.ts` |
| 14 | Guest account | Grant email | `display_name` = the address; `user.created` is written with the organisation and `purpose: 'auditor_access'` | A guest account belongs to exactly one organisation |
| 15 | CSV manifest hashes | E.7 columns | Cells pass the F.15 neutralisation, so a base64 quickXorHash that starts with `+` or `-` is written with a leading `'` | F.15 applies to every CSV writer |

## Follow-ups

- Orchestrator or WP-34 (optional): a scheduled sweep could call `AuditorAccessService.closeExpired(trx, orgId, now)` per organisation, for example from `cleanup.expired` (WP-22), so the membership is disabled and the `auditor_access.revoked` (reason `expired`) audit row is written at expiry rather than at the next grant list or grant. Sessions no longer depend on it: they expire with the grant. Until then the role and the sessions grant nothing from the expiry on.
- WP-27: the guest E2E reads the access link `/guest#<65-character token>` and the code (`Your one-time code is NNNNNN`) from Mailpit; the guest page posts the token to `/auth/guest/start` from the application's origin; the binding cookie path is `/api/v1/auth/guest/`; the test reset should also clear `platform.auth_transaction` rows of kind `guest_otp` and the `auth.guest.code` rate-limit buckets.
- WP-24: `evidence_pack_ready` notifications are created with `ref.entityType = 'evidence_pack'` and the label as code; the export area's `GET /tasks/{id}` (if any) can read the pack task's `result` (`packId`, `itemCount`, `exceptionCount`, `packFolder`, `repository`).
- WP-30: the RBAC and contract suites can cover the pack routes with the demo data used here; the guest routes are public with the Origin check.

## Plan findings

- E.7 does not say where manifests go when the default repository is link-only, nor what an archive contains when copies are spread over several repositories (deviations 4 and 5).
- F.14 step 5 needs a job (or a cleanup step) for expiry; E.2 has none (deviation 8).
- D.2 `EvidencePackRequest.scope` has no matching rule for clauses (deviation 10).
- F.3 does not say whether the per-grant limit counts failed link uses (deviation 3).
