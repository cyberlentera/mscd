# WP-37 handoff: audit registers and cycle derivation

## What was built

| Area | Files | Content |
|---|---|---|
| Findings | `apps/server/src/modules/audit-registers/findings.service.ts` | `GET /ms/{ms}/findings` (status, classification, source, `q` over code, title, clause, owner and status note; paging; `ScopePolicy`, so owner-scoped readers see their own findings and external auditors none), linked corrective actions and the audit event per row. `POST` (`finding.raise`): the audit event must be the path system's own or linked to it (404), owner through `MembershipService` (422 `NOT-A-MEMBER`), edition of the system, `raised_at` today, 409 for a live code, `finding.created`. `PATCH` (`finding.manage`, If-Match): changed fields only, `finding.updated` with before and after; a closed major finding keeps its RCA and systemic check (422 BR-06 or BR-07). Transitions through the C.13 table: closing runs BR-06, BR-07 and BR-08 through the engine, OFI, signal and not a finding need a close note (400), closing sets `closed_at`, `closed_by_user_id`, `close_note`; a reopen needs a reason, which becomes the status note, and clears the closure; `finding.transition` |
| Corrective actions | `corrective-actions.service.ts` | List with step texts, implementer, verifier and findings (`ScopePolicy`, owner or implementer for own scope). `POST` (`corrective_action.manage`): one or more findings, each resolved in the path system (404 otherwise), 409 for a live code, `corrective_action_finding` rows, `corrective_action.created`. `PATCH`: title, owner, due date, findings (replaced; not for a closed or cancelled action, 422), `register.updated`. Transitions: one step at a time with the step's text (400 without it, 409 for a skipped step), own grants for the owner (`corrective_action.update`), entering the verification records the implementer and the date; the verification (`corrective_action.verify`) checks BR-09 (verifier differs from implementer and owner) and, when closing, BR-08 (verification date differs from the implementation date); `effective: false` returns the action to the action step with a message; cancel needs a note; `corrective_action.transition` |
| Self-assessment | `self-assessments.service.ts` | One row per `ref.finding_condition` of the system's edition with its stored assessment (`not_assessed` and `ref: null` when there is none), filters and paging through `ScopePolicy`. `PUT .../{conditionCode}`: a new status through the C.13 table (the same status updates the other fields only), owner, target date, note, evidence codes of the system (422 for unknown codes), `assessed_at` today, `self_assessment.updated`. `POST .../{id}/raise-finding`: only from a gap (422), once (409 while the raised finding lives), code `SA-<year>-<nn>`, title from the request or the condition text, clause from the condition, owner and due date from the gap, source `self_assessment`; the assessment keeps the finding |
| Audit activity planner | `audit-activities.service.ts` | `GET .../audit-events/{id}/activities` (the event of the path system or linked to it), `POST .../generate` (`audit_event.manage`): the edition's templates of the event type, codes the event already has skipped, `count` = created, one `audit_activity.updated` entry with `created: true` per activity; `PATCH /audit-activities/{id}`: auditee (member, `none` clears), date, status, note |
| Management reviews | `management-reviews.service.ts` | List of the reviews linked to the path system with inputs per linked system (mandatory definitions and stored optional ones, `complete` when the content is not blank). `POST`: the path system must be in `linkedMs` (422) and is primary, other systems need `management_review.manage` there (403) and the `integrated_mode` feature, one empty input row per mandatory `review_input_def` per linked system (`count`), 409 for a live code. `PUT .../inputs/{defCode}`: the input of the path system (404 for a definition its edition lacks, 409 once the review is closed). Transitions: planned to held (`held_at` from the request or today), held to closed with BR-13 for every linked system (`affected` names the systems with an empty mandatory input) and BR-14 (decisions from the request or stored), `decisions_recorded`, `closed_at`, `closed_by_user_id`; closing queues `cycle.derive` for each linked system in the same transaction (`cd:<org>:<ms>`, 3 retries) |
| Rules | `rules.ts` | `@BusinessRule` providers BR-06, BR-07, BR-08 (finding closure and verification date), BR-09, BR-13, BR-14 (all errors) |
| `cycle.derive` | `cycle-derive.service.ts`, `cycle-derive.job.ts` | Handler `@JobHandler('cycle.derive', {scope: 'tenant'})`, so `scheduler.tick` now enqueues it at 03:15 local time (`cd:<org>:all`). For the current cycle of each system (latest `cycle_start`, as the read model picks it) and each item whose definition has a derivation: `management_review_closed` (a closed review linked to the system, closed within the cycle, every mandatory input of this system filled), `risk_assessment_current` (`months`, default 12; the system has risks and every one was assessed within the window), `internal_audit_done` (a finding of source `internal_audit` raised within the cycle), `exercise_performed` (an exercise performed within the cycle). A met requirement sets `done` (actor system, `cycle_item.updated` with the kind); otherwise the stored status stays; unknown kinds are skipped with a warning |
| Routes and module | `audit-registers.controller.ts`, `audit-registers.module.ts`, `index.ts`, `support.ts`, `README.md` | The 18 routes of `packages/shared/src/api/audit-registers.ts` through `@ApiRoute`; the module imports `JobsModule` (for `TenantJobRunner`). The contract file needed no change |
| Expired auditor grants (WP-26 verifier finding, F.14 step 5) | `apps/server/src/modules/jobs/tenant-cleanup.ts`, `jobs/cleanup-expired.job.ts`, `jobs/jobs.module.ts`, `jobs/README.md`, `apps/server/src/modules/auditor-access/auditor-access.module.ts`, `auditor-access.service.ts`, `auditor-access/README.md` | `TenantCleanupRegistry` (exported by `JobsModule`): modules register steps that the hourly `cleanup.expired` runs in a transaction of every active organisation as the system user; the job result has `tenantSteps` with a count per step. `AuditorAccessModule` imports `JobsModule` and registers `closeExpired` as step `auditorGrantsExpired`, so an expired grant revokes the guest sessions, disables the membership and ends the role within the hour, without anyone listing or creating grants. `closeExpired` now returns the number of grants it ended |

No migration was needed (`apps/server/migrations/tenant/37*.sql` not created): the C.6 CHECK constraints already back BR-06, BR-07, BR-08 and BR-09.

## Deviations and decisions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | Fixture pack for `cycle.derive` | "a fixture pack" | The tests add fixture rows to the installed framework content as the pack installer role (`ref.review_input_def` rows and `ref.cycle_requirement_def.derivation`), on the test database copy only | No demo pack defines review inputs or derivations (G.7); installing a second edition and moving a system onto it would test the pack installer, not the derivation |
| 2 | `internal_audit_done` | "a finding or audit event of source `internal_audit` in the cycle" | Findings of source `internal_audit` raised within the cycle | `audit_event` has no source column (C.6); its `event_type` values are certification body events |
| 3 | Current cycle | "current cycle" | The system's latest certification cycle (`cycle_start` desc), as the read model shows cycle items; "in the cycle" means between `cycle_start` and `cycle_end` | One rule for the screen and the job |
| 4 | Audit events of the path system | `RecordResolver` for `audit_event` | Own events (`management_system_id`) or events linked through `entity_ms_link` | Seeded events have no link row; WP-35 resolves them the same way |
| 5 | Ineffective verification | "`effective = false` returns it to `action` instead" | `to: 'closed'` or `to: 'action'` with `effective: false` returns to the action step (BR-09 applies, `verification_note` kept, no verifier stored); `to: 'action'` with `effective: true` is 400 | The verifier is recorded on the closing verification only, so the CHECK constraints stay meaningful |
| 6 | Cancel note | "note required" | Kept in the audit entry | `corrective_action` has no cancellation column |
| 7 | Audit actions | F.11 list | Corrective action changes `register.updated`; generated audit activities `audit_activity.updated` with `created: true`; raising from a gap writes `finding.created` and `self_assessment.updated` | `AUDIT_ACTIONS` has no `corrective_action.updated` or `audit_activity.created` |
| 8 | Same status on `PUT /self-assessments` | C.13 rows exclude a move to the same status | The same status updates owner, date, note and evidence without a machine row | The workbench saves notes and evidence of an assessment that keeps its status |
| 9 | Auditee from the template | `auditee_role` in the template | Generated activities have no auditee; the planner sets it | The template names a role label, not a user |
| 10 | Joint review rights | `management_review.manage` on the path | Also needed in every other linked system (403) | As WP-35 does for documents (F.7) |
| 11 | Expired grant sweep | "scheduled sweep for each active organisation" | A tenant step of the hourly `cleanup.expired` through `TenantCleanupRegistry`; steps run for active organisations only | `cleanup.expired` already runs hourly per organisation; the registry keeps `jobs` free of a dependency on `auditor-access` |
