# WP-09 handoff: pack and licence tooling

## What was built

`packages/pack-tools` is the library and CLI `mscd-pack` that build, sign and verify framework packs (E.8) and licences (D-15) with Ed25519 keys (D-16), plus the development keys and the development licences of G.3. `packages/pack-tools/README.md` documents the CLI, the pack format and every export.

| Area | Files | Content |
|---|---|---|
| Archive rules | `src/archive.ts` | `readPack(buffer, limits)`: gzip only, gunzip capped at `maxDecompressedBytes` (default 200 MiB), at most `maxEntries` (default 500) tar entries (`resolvePackLimits` merges limit by limit, so an absent, `undefined` or `null` limit keeps its default and can never turn a cap off; a limit that is not a positive safe integer throws `RangeError`), regular files only, no absolute paths (`/x`, `\x`, `C:x`), no `..` segments (with `/` or `\`), no control characters or backslashes, names unique after normalisation (`.` and empty segments dropped, Unicode NFC), files only at the root or directly under `mappings/`, and exactly `manifest.json`, `signature` and the files of `manifest.datasets` |
| Tar | `src/tar.ts` | Deterministic POSIX ustar writer (`writeTar`) and strict reader (`readTar`): header checksums, ustar magic, no extended headers applied, truncation and trailing data refused, entry cap checked before an entry is read |
| Build and verify | `src/pack.ts`, `src/build-all.ts` | `buildPack(sourceDir, signingKey, {rejectKeyIds})` reads a source folder (regular files only, `mappings/` the only subfolder, no `signature`), validates the manifest and every dataset, writes the dataset checksums into `manifest.json` (E.8 member order, two-space indentation), signs its exact bytes and writes the archive: entries sorted by name, then `signature`, mtime 2026-01-01T00:00:00Z, uid and gid 0, mode 0644, gzip level 9; the result is checked with `verifyPack` before it is returned. `verifyPack(buffer, trustedKeys, {rejectKeyIds, limits})`: `readPack`, then the signature file, refused key ids, a trusted pack key, the signature, the manifest schema, every checksum and every dataset. `buildAllPacks` builds a whole sources folder, writes atomically and removes stale `.pack` files |
| Datasets | `src/datasets.ts`, `src/csv.ts` | `parsePackDatasets(files, manifest)`: the 17 dataset files of E.8 present, no unknown files, UTF-8 without BOM, LF only, the E.8 CSV headers, every row and JSON document through the schemas of `@mscd/shared` (csv-parse 7.0.3 with strict quoting), then references a pack can check alone (unique codes and keys, parent and catalogue requirement codes, frequencies, label keys in both languages and theme labels, required lookup domains, document template types, risk profiles of chain stages, one name per phase, mapping sources, the `catalogue` flag). Returns typed rows for the installer |
| Licences | `src/licence.ts` | `signLicence(doc, key, {rejectKeyIds})` sets `key_id`, signs the canonical JSON without `signature` and checks schema and binding; `verifyLicence(doc, trustedKeys, {rejectKeyIds})` takes text, a buffer or an object and checks schema, refused key ids, a trusted licence key, the signature and the binding rule (bound, or a trial of at most 90 days) |
| Keys | `src/keys.ts`, `src/key-id.ts`, `src/dev-key-ids.ts` | Ed25519 generation and loading; `trustedKeysById` accepts key objects, PEM texts and the server's `TRUSTED_KEYS` entries; an entry with a `kind` is used only for that kind (a licence key never verifies a pack, A-17) and a stated `keyId` must match the key |
| Errors | `src/errors.ts` | `PackError` (`archive`, `manifest`, `signature`, `untrusted_key`, `rejected_key`, `checksum`, `dataset`, `source`, `signing_key`) and `LicenceError` (`format`, `signature`, `untrusted_key`, `rejected_key`, `binding`, `signing_key`), each with the list of every problem found |
| CLI | `src/cli.ts`, `src/commands.ts` | `keygen`, `build`, `build-all`, `verify`, `licence sign`, `licence verify` as in the brief; exit 0, 1 (failure, one message) or 2 (usage). The package `postbuild` script marks `dist/cli.js` executable, so the `mscd-pack` bin also runs after a build in a clean checkout |
| Development keys | `dev-keys/` | Ed25519 pairs `pack-signing` (`f4c7f82942491de1`), `licence-signing` (`f83c3c5b683ceb05`) and `anchor-signing` (`0abdc91769bacddd`), the copies `pack-dev.pub`, `licence-dev.pub` and `anchor-dev.pub`, `dev-key-ids.json` with the three ids, and a `README.md` stating they are for development and demo only. `apps/server/scripts/gen-build-info.mjs` now compiles the three keys into a dev build, and in release flavour refuses this folder ("holds development keys") |
| Development licences | `dev-licences/LIC-DEMO-NDT.json`, `-BSD`, `-RMN`, `-TST` | G.3 licences signed with `licence-signing.key`, bound to `00000000-0000-4000-8000-00000000a001` to `a004`, valid 2026-04-01 to 2027-03-31, grace 30 days, the four frameworks, 10 systems, 150 users, the four adapters and four features of G.3 |
| Tests | `test/*.test.ts` | 80 tests: tar format and readability by node-tar and GNU tar; every archive rule (traversal, absolute paths, symbolic and hard links, folders, FIFOs, devices, pax and GNU entries, an archive made by node-tar with a link, duplicate names also after normalisation and NFC, files outside the root, extra and missing files, entry cap, a 200 MB decompression bomb of about 200 KB, the default caps kept for limits passed as `undefined` or `null` through `readPack` and `verifyPack`, invalid limits refused, bad gzip, invalid UTF-8 names); determinism, checksums, signature, tampered manifest, forged and malformed signature files, checksum mismatch, signed packs with invalid manifests or datasets, untrusted keys, kind filtering; `rejectKeyIds` refusing a pack and the four licences signed with development keys; source folder faults; licence signing, tampering, binding and trial rules; the development keys and licences; the CLI in process, including `--reject-dev-keys` failing closed when `dev-key-ids.json` is missing |

Dataset counts printed by `mscd-pack verify` for the six development packs (requirements, catalogue, chain stages, activities, lookups, rules): ISO27001-2022 1.2.0 24, 93, 8, 69, 11, 40; ISO9001-2026 0.9.0 and ISO9001-2015 1.4.2 28, 0, 8, 57, 11, 39; ISO22301-2019 1.0.0 27, 0, 8, 43, 15, 39; ISO37001-2025 0.6.0 (pre-release) and ISO37001-2016 1.0.0 (withdrawn) 32, 0, 6, 43, 19, 40.

## Deviations and additions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | Tar implementation | A.1 names `tar` 7.5.22 for pack archives | Archives are written and read by `src/tar.ts` (POSIX ustar, under 300 lines). node-tar is used in the tests as an independent reader and to make an archive with a link | node-tar takes mode and owner from the files on disk (umask dependent, so not deterministic across machines) and its parser applies pax headers and detects compression by itself, so a nested gzip stream would bypass the decompression cap. The archives stay standard: GNU tar and node-tar read them. `tar` stays in `dependencies` (see follow-ups) |
| 2 | Extension entries | E.8: regular files only | pax extended and global headers and GNU long name and long link entries are refused like links and folders | They can rename the next entry; packs never need them (all names fit ustar) |
| 3 | Extra path rules | No absolute or `..` paths | Also refused: control characters, backslashes, names that are not valid UTF-8. NFC normalisation for the duplicate check | Names that mean different files on different systems |
| 4 | Size cap unit | "200 MB decompressed" | 200 MiB (209,715,200 bytes) of tar stream after gunzip | One unambiguous number; `DEFAULT_PACK_LIMITS` |
| 5 | Dataset validation in `verifyPack` | E.8 step 3 is the installer's | `verifyPack` validates every dataset with the shared schemas and the in-pack references and returns typed rows; the installer keeps the checks that need the server (chain entity types of C.10, `engine_min_version`, installed versions) | `mscd-pack verify` reports an uninstallable pack, and WP-12 gets parsed rows |
| 6 | Encoding rules | Not stated for archives | Datasets must be UTF-8 without BOM with LF line endings (the `packs/README.md` source format), in sources and archives | One parser behaviour for build and install |
| 7 | `--reject-dev-keys` | Not in the brief | Option of `build`, `build-all`, `verify`, `licence sign` and `licence verify`: refuses the ids of `dev-key-ids.json` with a "development key" message; fails closed (exit 1) when that file is missing | WP-18's release stage must fail on a development `pack_signing_key` with a message containing "development key" |
| 8 | Other CLI options | Brief lists the commands | `keygen --force` (existing files are kept otherwise; `.key` written with mode 0600), `build-all --sources <dir>` (default: `packs/sources` of the repository, found from the package location, so the command works from any folder), `licence sign --out <file>` (default prints the signed JSON) | Safe defaults; the release image builds from `/app` |
| 9 | Stale packs | Not stated | `build-all` removes `.pack` files of the output folder that no source produces (for example after a version bump) and prints them; other files are kept | `packs/dist` holds exactly the current packs, so the seed never installs an old version |
| 10 | Licence binding | Server rejects unbound licences (422 `LIC-BINDING`) | `signLicence` and `verifyLicence` refuse an unbound licence that is not a trial of at most 90 days with code `binding`; the bound id is returned for the server to compare | A licence that can never be accepted is caught when it is signed |
| 11 | Licence member order | Not stated | Members keep their input order with `key_id` and `signature` last; a leading byte order mark in a licence file is ignored | Readable files; the signature covers the canonical form only |
| 12 | Development private keys | Not stated | Committed with mode 0644 | They are public development keys; a 0600 file owned by another user would break Docker build stages that sign with them. `keygen` still writes 0600 for real keys |
| 13 | `canonicalJson` | Library export | Re-exported from `@mscd/shared` (WP-05 owns the implementation) | One implementation for licences, anchors and credential bindings |

## Follow-ups

- WP-12: verify with `verifyPack(bytes, TRUSTED_KEYS, {rejectKeyIds: BUILD_FLAVOR === 'release' ? DEV_KEY_IDS : []})` and `verifyLicence(doc, TRUSTED_KEYS, ...)`; the `kind` of each `TRUSTED_KEYS` entry selects pack or licence keys. Map `LicenceError` code `binding` to 422 `LIC-BINDING` and the other codes to 400; map `PackError` to `pack.rejected`. In a release image `DEV_KEY_IDS` is empty (no `dev-keys/`, R-13), so the rejection there is defence in depth behind `gen-build-info.mjs`. The J.5 hostile archive cases can be made with `writeTar` and `gzipSync`, as `test/archive.test.ts` does.
- WP-14: `ensure-built.mjs` can run `build-all` as in the acceptance; the seed reads `dev-licences/LIC-DEMO-<SLUG>.json`.
- WP-18: in the release stage run `node packages/pack-tools/dist/cli.js build-all --reject-dev-keys --sign-key-file /run/secrets/pack_signing_key --out /packs`. The build stage needs `packages/pack-tools/dev-keys/dev-key-ids.json` (the final image must not contain it, R-13); without it the command exits 1 instead of signing unchecked.
- Orchestrator: `tar` is used only by the tests now and could move to `devDependencies` of `@mscd/pack-tools` between waves (a lockfile change, so not done here).
- WP-05 was in its fix round during this work; the tests import the shared schemas from source, so a later change there shows up in `npm test -w @mscd/pack-tools`.
