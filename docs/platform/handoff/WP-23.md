## Deviations and decisions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | Folder comparison | `current.folderPath <> stored folder` | Segments trimmed, empty ones dropped; Microsoft 365 without regard to case. The stored folder is rewritten only when the item really moved | The seeded paths use ` / ` as separator; a literal comparison made every demo file `moved` |
| 2 | `moved` | Recomputed every check | Stays `moved` while the item is found where it went (the stored folder follows the item) | Otherwise a move is visible for one day only, since the folder is stored on the first check |
| 3 | Vault `hash_mismatch` | Not stated | The link check keeps `hash_mismatch` of a computed hash; only a new file clears it; broken objects are not re-hashed again | The vault `stat` has no hash to compare, so the next check would reset the re-hash finding to `intact` |
| 4 | Instants | `now()` | `windowNow` (WP-22): `link_status_since`, `last_verified_at`, `last_good_check_at`, `checked_at`, `last_checked_at`, drift `detected_at` and `resolved_at` | With `demo.fixed_today` the windows are measured on the fixed date; the stored instants must agree |
| 5 | `link_health_result` | A row on a status change | Also a `rate_limited` row for the throttled object and a row per re-hash (`detail.check = 'rehash'`) | History of throttling; the re-hash needs a last-run time and `storage_object` has no column for it |
| 6 | Rescheduled rest key | `lhc:<org>:<repo>:<sha1 of ids>` | The hash also covers the time the rest may run | When the first object is throttled the rest equals the running batch, whose key is still taken |
| 7 | Gateway problems in `stat` | Outcomes only | Credential problems (`credential-binding`, `credential-missing`, `credential-kind`) count as `unreachable`/`credential_invalid`; `outside-root` and other refusals keep the status (logged, the object stays due) | An item outside the root is already a `forbidden` outcome of the adapters; a refused id is a data error, not a provider state |
| 8 | Repository messages | Set on every test | Set when the status changes, cleared when it turns `ok`; `last_checked_at` on every test | The message describes the state since it began; the demo keeps its seeded texts |
| 9 | Connector alerts | `revoked` raises an alert | One per served system (default repository, root folder in `config.roots`, active routing rule), matched by `source_ref.repositoryId` or by the seeded `source_ref.repository` slug; resolved when the repository is `ok` again; `failed` keeps an open alert | The seed stores `{repository: <slug>}`; a revoked app turning into another failure is still broken |
| 10 | `credential_expiring` dedupe | 30 and 7 days | The notification's ref code is `<slug> 30d` or `<slug> 7d`; a step is sent once per credential | `notification` has no column for the step |
| 11 | Live drift rules | Rows for every computed kind | Stored for `unverif`, `nohash`, `metric` and `exercise` too (with notifications), although the read model shows these rules from their source lists | E.2 gives every computed kind rows; the rows feed notifications and later reports |
| 12 | `dd_expired` "above low" | Not defined | Any level other than `low` (the pack lookup `bribery_risk_level`: low, medium, high, very_high) | Simplest reading of the packs |
| 13 | Feature gate of the plan | Only with `link_health_monitor` | The plan does nothing without the feature; checks queued by the route need the feature at request time; `link-health.repository`, `drift.evaluate` and `integrity.rehash` run regardless | E.2 names the feature for the plan only |
| 14 | J.4 parity test | `test/int/parity` | `test/int/jobs-health/demo-parity.test.ts` (with the WP-17 comparator) | `test/int/parity` is not a WP-23 path (R-01) |
| 15 | Key of a batch of the on-demand run | `lhc:<org>:<repo>:<sha1 of ids>` | The hash also covers the task id, for the first batch and for any rescheduled rest | Two runs of one system have the same batches; without the task id the second run's checks were dropped as duplicates and its task stayed `queued` |
| 16 | Run progress | Not stated | `result.checked` moves once per check job, at its end (or for the part done before a throttled rest is queued again); `result.changed` moves as each change commits | A batch retried after a transport failure is checked again from its first object; counting per object counted it twice and ended the run early. A status change is not applied twice, so `changed` cannot double |
| 17 | Re-hash selection | Not stated | The 7-day window, the order (never re-hashed first, then oldest) and the 200 cap run in SQL | Reads stay at 200 rows whatever the vault size |

## Plan findings

- G.9 and the repository check: `GET /ui/org` cannot stay equal to the sample after `link-health.repository`, since `REPOS[].last` shows the time of the last check, and the G.8 OneDrive answers 403 to every request while the sample shows the repository as working (status `warn` for a personal repository). The job stores `failed` for it. The parity test asserts these two changes instead.
- The demo vault objects (`tenants/<org>/demo-vault-<code>`) are not vault object ids, so the gateway refuses them (`outside-root`) and they have no stored bytes. The checks keep their status (deviation 7), but a demo installation can never verify or re-hash them; WP-14 could seed them through the gateway with content.
- The demo metrics have no `frequency_code` and the demo BCMS has no `bc_plan` rows, so the `metric` and `exercise` drift rules find nothing on the demo data; the tests add the data they need.
- E.2 lists `drift.evaluate` "after `freshness.recompute`"; the freshness module (WP-22) does not queue it yet, so new unverifiable files show up in stored drift rows at the next daily run (the UI reads those rules live, so nothing visible lags).
- `StatResult` has no detail for a refused id or a trashed parent folder (WP-15 finding); the history rows record the gateway slug in the log only.
