# WP-21 handoff: file commands

## What was built

| Area | Files | Content |
|---|---|---|
| Module | `apps/server/src/modules/files/files.module.ts`, `files.controller.ts`, `README.md` | The nine routes of the `files` area (D.3) through `@ApiRoute`. Imports `StorageModule`; exports `UploadsService` and `FileCommandsService` |
| Common steps | `files-common.ts` | System by slug with its code, the permission of the record kind (`evidence.file.submit` or `document.version.create`, own or full), the record through `RecordResolver` with the owner check of own grants, storage object rows, gateway object refs, the systems of an evidence record (links and targets) and of a document |
| Rules and mapping | `files-support.ts` | Rule texts of BR-23, BR-29, BR-30, BR-35, BR-36 in both languages; BR-29 before every gateway call (connection status not `ok`, read-only repository, adapter not enabled in the profile, adapter not licensed); gateway refusals mapped to the D.3 answers (`unreachable`, `rate-limited` and credential refusals to 422 BR-29, `outside-root` to 422 `files.outside_root`, `not-found` to 404, zero-transit refusals to 422 `files.item_refused`, the api's own token or certificate refused to 503); scope roots (`config.roots[<ms>]`, 404 without one; the vault label is the system code); stored names; correlation codes; document version labels |
| Browse and uploads | `uploads.service.ts` | Browse below the system root (gateway `list`, up to ten pages, picker tuples of UI 1.15); upload intents (routing with the record's classification and kind, A-37; a `link` rule falls back to the repository's first upload mode, else 422 `files.no_upload_mode`; size limit 413; stored name `<code>-<sequence>.<ext>` and no original name under metadata minimisation; folder `Evidence/<year>/Q<n>` or `Documents` below the system root; one hour); `PUT .../content` (creator only, else 404; open, unexpired, stored or pass-through, else 409; declared size enforced, 413; the record and BR-29 checked again; the body streamed from the raw parser to the gateway; Google Drive versions pinned before the object is recorded); `POST .../complete` (zero-transit, gateway `register-client-upload` with folder, `notBefore` = intent creation, correlation code and the creator's email) |
| Content-Length | `gateway-upload.ts` | `PUT /v1/objects` with the browser's `Content-Length` (needed for Microsoft 365 upload sessions above 4 MiB, WP-15 deviation 6), same settings, token file and mTLS agent as `HttpGatewayClient`; without a length, or with a test double of `GATEWAY_CLIENT`, the shared `putObject` is used |
| Evidence files and document versions | `file-commands.service.ts`, `storage-objects.ts`, `evidence-state.ts` | Link (gateway `link`, repository must offer `link`), upload and client upload (intent of the caller for this record and system, mode matching the source, `uploaded`, else 409 `files.intent_mismatch` or `files.intent_not_uploaded`); `submit` raises `file_sequence`, `relink` keeps it and is 409 `files.relink_not_needed` while the current file is intact or moved; `producedAt` defaults to today and may not be in the future; the evidence's freshness and integrity are derived with the E.3 functions of the read model in the same transaction; `freshness.recompute` is queued per system of the evidence (singleton `fr:<org>:<ms>`, 5 seconds); warnings BR-30 (personal repository), BR-36 (`producedAt` more than one day after the file's creation date), BR-23 (a target in another system reached through a mapping with `evidence_reusable = false`); audit `evidence.file_linked` or `evidence.file_uploaded`. Document versions: 409 while a version is in review, new `document_version` in `in_review`, document `in_review` (A.4 5.7), audit `document.version_created` |
| Objects | `object-access.service.ts`, `redirect-token.ts` | `open`: `ScopePolicyService.scopeContext` plus `canReadObjectIn` (404 otherwise), the content URL for vault and pass-through files, the redirect URL for linked and zero-transit files, audit `file.opened`; `redirect`: token (HMAC of `platform.key` via `SecretBox`, purpose `storage-redirect`, user, organisation, system, object, 5 minutes; 403 when tampered, expired, for another user or object), `storage.object.read` evaluated again, scope checked again, never for external auditors (404), gateway `open-url`, 302; `content`: 422 BR-35 for linked and zero-transit files, gateway `stream`, `FileResponder` with the stored detected type (F.13), audit `file.downloaded`. External auditors open only pack copies of ready packs, always through the content route, and their reads list the record behind the file (`addAuditorReadRefs`) |
| Contract | `packages/shared/src/api/files.ts` | `EvidenceFileRequest.producedAt` optional (today when omitted, WP-21 brief); `BrowseQuery.path` refuses `.`, `..`, backslashes and control characters (400) |

Mime types: `storage_object.mime_type` is only ever the gateway's `detectedMimeType` (uploads, and provider items when the gateway reports one); a provider-declared type is never stored.

## Deviations and decisions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | Permission per record kind | `evidence.file.submit` or `document.version.create` (own) | The route keeps `anyOf` (the shared route test lists the `anyOf` routes); the service evaluates the permission of `kind` and answers 403 without it | A Domain Owner with only `evidence.file.submit` must not prepare document uploads |
| 2 | Content-Length | `GATEWAY_CLIENT.putObject` | `GatewayUpload` repeats the PUT with `Content-Length` | `putObject` (WP-13) takes no length; see follow-ups |
| 3 | Intent status | `open`, `uploaded`, `completed` | `uploaded` after content or completion, `completed` when attached; failed gateway calls leave the intent `open` for a retry | One upload attaches once |
| 4 | Intent size | `maxBytes` | The declared size (at least 1), checked against `storage.max_upload_bytes` | The browser knows the size; a longer stream is refused |
| 5 | Folders | TS 5.4 convention | `Evidence/<year>/Q<quarter>` and `Documents` below the system root; the vault scope root is the system code | Matches the demo layout; cycle folders need the cycle naming of WP-37 |
| 6 | Relink | Not defined | Allowed only while the current file is not `intact` or `moved`; keeps `file_sequence` | Relink repairs a broken link; a new file is a submission |
| 7 | Document version labels | Not defined | Linked and pass-through: the provider label without the leading `v` (`3.0`, `rev 2`), 409 `files.version_exists` when already recorded; vault: the `document_version` label is the next major version after the stored labels (`4.0`), as the sample does, while the vault `storage_object` keeps its upload label `v<file_sequence>` (brief) | Document labels are stored without `v` by the seed |
| 8 | Current document version | Not defined | `document.current_version_id` stays on the approved version while the new one is in review | The register shows the version in force; WP-35 approval moves it |
| 9 | BR-35 | Zero-transit preview | `content` answers 422 BR-35 for every linked or zero-transit file (the api streams only vault and pass-through files) | D.3 limits content to those two; the rule text fits both |
| 10 | External auditor copies | Pack copies only | Opened only through the content route; a copy in a repository without pass-through is 422 `files.copy_not_streamable` | D-34: no provider URL for auditors |
| 11 | BR-29 detail | Repository not ok, gateway unreachable, adapter | Also read-only repositories and a provider refusing the credential | Neither can serve a file |
| 12 | Rules engine | WP-20 engine | The file rules are applied directly in this module, always active | The engine was built at the same time; every demo pack activates BR-23, BR-29, BR-30, BR-35 and BR-36 |
| 13 | Google Drive pins | Pin the linked or uploaded version | `/v1/pin-version` runs before the transaction that records the object, with the ref built from the gateway's metadata or put result; no row lock is held across the call | When recording then fails (a race on the intent), the provider revision stays kept with no `storage_object` row, which is harmless |

## Follow-ups

- WP-13 owner or orchestrator: add an optional `contentLength` to `GatewayClient.putObject` (`src/common/tokens.ts`, `src/modules/storage/gateway-client.ts`); `GatewayUpload` can then call it and drop its copy of the client setup.
- WP-35 (document approval): approving the `in_review` version should set `document.current_version_id`, mark the earlier approved version `superseded` and clear `review_started_at`.
- WP-22 (`cleanup.expired`): intents left `uploaded` but never attached keep their storage object; a cleanup step could delete those objects after the intent expires.
- WP-26: pack copies are opened through `GET /storage/objects/{id}/content`; `copy_storage_object_id` objects in a repository without pass-through cannot be read by auditors (deviation 10).
- WP-25: `POST /storage/upload-intents` then `PUT contentUrl` (raw bytes, `Content-Length` set) then `POST /ms/{ms}/evidence/{id}/files` with `source: 'upload'`; zero-transit uses `complete` and `source: 'client_upload'`; `open` answers a URL to navigate to.

## Plan findings

- D.3 lists no 409 for `PUT .../content` racing another request on the same intent; the second request gets 409 and its stored object stays unreferenced.
- `ref.requirement_mapping` maps requirements only, so BR-23 never fires for evidence that targets catalogue items (Annex A controls) on both sides.
