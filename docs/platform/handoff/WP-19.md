# WP-19 handoff: SAML sign-in

## What was built

| Area | Files | Content |
|---|---|---|
| SAML sign-in | `apps/server/src/modules/identity/saml/saml-sign-in.service.ts`, `saml.controller.ts` | `GET /auth/saml/{slug}/start`: 404 for an unknown, disabled or non-SAML provider, a kind the profile does not offer, or an archived organisation. An `?invitation=` token must name an unused, unrevoked, unexpired invitation of the provider's organisation, else `/login?error=invitation_invalid` and no transaction is written. An `auth_transaction` (`saml_login`) holds the SHA-256 of a random state (sent as `RelayState`) and of a browser binding value, the AuthnRequest id in `saml_request_id`, the relative `return_to` and the invitation id in `target_id`, for 10 minutes. The binding value goes to cookie `mscd_saml_tx` (`HttpOnly`, `Path=/api/v1/auth/saml/`, 10 minutes; `Secure; SameSite=None` with `security.cookie_secure`, else `SameSite=Lax`, F.9). Redirect to the HTTP-Redirect URL of an unsigned AuthnRequest (persistent NameID policy with `AllowCreate`, ACS URL `<http.public_url>/api/v1/auth/saml/<slug>/acs`, no requested authentication context, `ForceAuthn="true"` for links and invitations). `POST /auth/saml/{slug}/acs`: `DELETE ... RETURNING` of the transaction by the `RelayState` hash, binding cookie compared in constant time, expiry by the server clock, the slug must be the transaction's provider and the provider still usable, then `@node-saml/node-saml` (signed assertion required, the outer response may be unsigned; `Conditions` timestamps with 60 seconds of skew; audience equal to the SP entity id), then the rules below. The binding cookie is always cleared; every failure redirects to `/login?error=<code>`. `GET /auth/saml/{slug}/metadata`: SP metadata (`application/samlmetadata+xml`) with the entity id, the HTTP-POST ACS, the persistent NameID format and `WantAssertionsSigned="true"`; served for SAML providers of organisations that are not archived, also while the provider is disabled (so the identity provider side can be prepared first), else 404 |
| Assertion rules | `saml-rules.ts` | Facts read from the signature-checked assertion only (`profile.getAssertion()`): id, issuer, NameID and format, bearer confirmations, `Conditions/@NotOnOrAfter`, `AuthnContextClassRef`, email attribute. Issuer must equal `saml_idp_issuer` when set (the library checks signatures, not the assertion issuer). The assertion id is inserted into `platform.saml_assertion_seen` until the latest `NotOnOrAfter` plus the skew, in its own committed transaction before the later checks, so a replay fails even when the first use failed afterwards; an assertion without any `NotOnOrAfter` is refused. A bearer confirmation must answer the transaction's request (`InResponseTo`; the outer response's `InResponseTo` must match too when present), be addressed to this ACS (`Recipient`, when given) and be valid. The subject is the persistent NameID; another format is `idp_error` |
| Identity paths | `saml-sign-in.service.ts` | F.8 step 4 without JIT (F.9): an existing `user_identity (provider, NameID)` (with an invitation in the transaction it must be that user's invitation, which is then redeemed); a `saml_link` transaction links the NameID to the transaction's user (`link_method = 'session'`, `identity.linked`, `security` email `identity_linked`; a NameID linked to another account is refused); an invitation links the NameID (`invitation`), activates the membership after `LicenceGate.assertCanAddUser` and an `invited` account, marks the invitation used (`identity.linked`, `membership.updated`). Otherwise `no_account`, also when an account has the asserted email. `email_at_link` stays null. The account must be an active person with an active membership in the provider's organisation |
| MFA and session | same | With `require_mfa_claim`, an `AuthnContextClassRef` in `saml_mfa_authn_contexts` proves MFA: session `active` at once, `amr = ['mfa']`, `auth.login` with `method: 'saml'`, provider id and slug, subject, `secondFactor: 'idp_mfa'` and `authnContext`. Without proof: `reject` gives `mfa_required_by_policy`; `local_totp` (and `require_mfa_claim = false`) continue to `mfa_pending` or `mfa_enrolment` with a redirect to `/login/mfa#csrf=<token>` or `/login/enrol#csrf=<token>`; the MFA routes of WP-11 finish the sign-in. The session has `auth_method = 'saml'`, `identity_provider_id`, `organization_id` and `auth_org_id` set to the provider's organisation (D-26); a session cookie presented with the ACS post is revoked (`signed_in_again`). `user_identity.last_login_at` is stamped |
| Failure codes | same | `expired`: unknown or used `RelayState`, missing `RelayState`, expired transaction, missing or wrong binding cookie, another provider's ACS, `InResponseTo` of another request, a replayed assertion id, a link whose user is no longer an active member. `idp_error`: signature, audience, timestamps, status other than success, issuer, NameID format, recipient, missing validity, provider disabled meanwhile, a NameID linked to another account (link), unexpected errors. `no_account`, `invitation_invalid`, `mfa_required_by_policy` as above. Refusals of a known transaction audit `auth.login_failed` with the provider's organisation (`entity_type` `identity_provider`, `after_data` `{method: 'saml', flow, error, reason}`) |
| Identity linking | `saml-sign-in.service.ts` | Registers the SAML starter with `IdentityLinkRegistry` (WP-16) in `onModuleInit`; `POST /me/identities/{slug}/link` for a SAML provider returns the HTTP-Redirect URL of a `saml_link` transaction and sets `mscd_saml_tx` |
| Module | `saml.module.ts` | `SamlModule` (controller, service; imports `OidcModule` for the registry) |
| Contract | `packages/shared/src/api/auth.ts` (SAML routes) | Start and ACS get the per-address limit of the OIDC start route (300 per 15 minutes) and list 429; summaries describe the redirects |
| README | `identity/saml/README.md` | Files and behaviour |

## Tests

`apps/server/test/int/sso/saml.test.ts`, with the Keycloak of `test/setup/keycloak.ts` (WP-16) and the realm's SAML client `mscd-dev-sp`. Keycloak users are created per test and deleted afterwards; their persistent NameID (`G-<uuid>`, assigned by Keycloak at the first SAML sign-in) is read from the response and pre-registered where a test needs a linked account. The IdP certificate comes from the realm's SAML descriptor. The application is the one of the OIDC suite plus `SamlModule` (`AdminIdpModule` loads `OidcModule`, as the api does), no mail server.

## Deviations and additions

| # | Item | Plan | Built | Reason |
|---|---|---|---|---|
| 1 | Rate limits | F.3 lists none for SAML | Start and ACS: 300 per 15 minutes per address (the OIDC start limit), 429 in the contract | Every start writes a transaction row; every ACS post checks an XML signature |
| 2 | Link ACS and the session cookie | F.8: the link callback needs the signed-in transaction user in the same browser | The SAML link ACS checks the binding cookie (set on the signed-in `POST /me/identities/{slug}/link`) and that the transaction's user is still an active person and member; it does not read the session cookie | The ACS is a cross-site form post: browsers never send the `SameSite=Lax` session cookie with it. The `SameSite=None` binding cookie, set only on the signed-in request, ties the post to that browser |
| 3 | Order of checks | F.9 lists the checks | Assertion id cache before `InResponseTo` | A captured assertion is consumed whatever else is wrong with the post, and the replay test proves the cache itself |
| 4 | Session `amr` | Not specified for SAML | `['mfa']` when `AuthnContextClassRef` proved MFA, else empty; the context values go to `auth.login` | SAML has no `amr` claim; `mfa_at` stays null as for OIDC (WP-16 deviation 9) |
| 5 | Metadata of a disabled provider | Not specified | Served while the provider is disabled | The identity provider side is usually set up before the provider is enabled; the metadata holds no secret |
| 6 | Default SP entity id | `spEntityId` is required by the admin contract | When the column is null, the metadata URL `<public_url>/api/v1/auth/saml/<slug>/metadata` | Rows written by other means (seed, CLI) still get a stable entity id |
| 7 | Assertion time checks | The server clock | The library checks timestamps with the system clock; the bearer confirmation check uses the same clock | Both checks of one assertion agree; the application clock differs from the system clock only in tests |

## Follow-ups

- Orchestrator (blocking for the api, outside this package): `SamlModule` is not loaded by the api yet. The SAML routes and SAML linking work once one line is added to `apps/server/src/modules/admin-idp/admin-idp.module.ts` (WP-16): `import { SamlModule } from '../identity/saml/saml.module';` and `imports: [OidcModule, SamlModule]`. Loading it through `apps/server/src/app/feature-modules.ts` works as well. That file of WP-16 was under WP-16's final polish during this package, so it was not edited here. The SAML suite builds its application with `SamlModule` explicitly and proves the module works next to `AdminIdpModule` and `OidcModule`. Until that line is added, the running api and worker do not mount `/auth/saml/{slug}/start`, `/acs` and `/metadata`, and `POST /me/identities/{slug}/link` has no starter for a SAML provider; the passing SAML suite does not prove the wiring. After the change, a check such as `grep -n SamlModule apps/server/src/modules/admin-idp/admin-idp.module.ts` and one start request against the api run mode confirm it.
- WP-22: `cleanup.expired` deletes `platform.saml_assertion_seen` rows past `expires_at` and unfinished `saml_login` and `saml_link` transactions (E.2 already lists both).
- WP-16 or WP-30: the identity paths (existing link, invitation, link transaction) exist twice, in `oidc-sign-in.service.ts` and `saml-sign-in.service.ts`, because the OIDC ones are private to that service. A shared `IdentityMapper` in `identity/` would keep the two in step.
- WP-14 (seed): a seeded SAML provider for the Keycloak SAML client needs `saml_entry_point` `<issuer>/protocol/saml`, `saml_idp_issuer` the realm issuer, the realm's signing certificate from `<issuer>/protocol/saml/descriptor` as PEM, and `saml_sp_entity_id` `mscd-dev-sp`.
- WP-11 (finished): as for OIDC, a sign-in that ends at the local TOTP step writes `auth.login` without the subject (WP-16 follow-up).

## Plan findings

- F.2 and F.8 ask the link callback to check the signed-in user; for SAML that cannot use the session cookie (deviation 2).
- F.9 does not say where the subject confirmation's `InResponseTo` and `Recipient` are checked; `@node-saml/node-saml` checks the outer response's `InResponseTo`, which the identity provider may leave unsigned, so this package checks the signed confirmation itself.
- The identity subfolders still have no place in `feature-modules.ts` or `identity.module.ts` (WP-16 finding); see the first follow-up.
